# Hunter 阶段一产品可实现性评估

> 日期：2026-09-02  
> 范围：《Hunter 阶段一产品概要设计》、在线 `00—13` 产品详细设计、当前高保真原型，以及 Hunter 本地版已有公司 Agent、岗位 Agent、信息补全、人岗匹配、人才地图和学术数据实现。  
> 目的：判断每项产品能力不仅能否开发，还能否达到用户预期的业务效果；明确正式技术方案前必须完成的验证。

## 一、结论摘要

Hunter 阶段一的产品骨架可以实现，账号、资产管理、统一任务、运行恢复、审核写入、版本、回收站、设置和运营端均属于成熟工程问题。公司分析、岗位分析、人才关系、岗位重点人才梳理和候选人信息补全也可以形成有价值的产品，但它们不是“只要接入大模型就能稳定得到真相”的功能，效果取决于数据覆盖、身份统一、证据质量、时间有效性和人工确认。

阶段一可以承诺：**在明确范围内，基于用户资料、系统资产和可合法使用的公开来源，生成带证据、置信度、缺口和待确认项的分析结果，并在底层数据变化后增量更新。**

阶段一不能承诺：

1. 完整摸清市场上所有人才、某公司的实时组织架构或全部招聘需求。
2. 仅凭公开信息稳定获得私人手机号、汇报关系、求职意愿或未公开的人才流动。
3. 对同名人物、同名公司或复杂经历永不误合并。
4. 所有公开网页都可访问、所有第三方数据源始终可用，或 Agent 每次都得到同样结果。

如果把产品定位为“证据支持的猎头研究、关系整理和决策辅助系统”，整体可行；如果把结果包装成“完整、实时且确定的人才市场事实”，则不可行，也会放大合规和信任风险。

## 二、评估基线与口径差异

### 2.1 资料优先级

本评估按以下顺序解释当前产品：

1. 已确认的最新产品决策和在线 `00—13` 详细设计。
2. 当前高保真原型中的页面、状态和交互。
3. 《Hunter 阶段一产品概要设计》中的长期目标和仍然有效的原则。
4. Hunter 本地版代码只作为已有技术基础和历史验证证据，不自动等同于 SaaS 最终方案。

### 2.2 已发现的基线差异

概要设计仍使用“业务主线 / 支线任务 / 配套寻访 App”等旧口径；最新详细设计和原型已经统一为用户只创建和管理“任务”，资产页中的确定性 AI 操作不进入任务列表，并取消云端与本机寻访 App 通信协作，只保留用户上传文件和公开网络信息。

这不阻止研发开始租户、资产、任务运行、证据、版本、审核和运营能力的架构评估，但会影响任务分类、来源边界和渠道范围的估算。概要设计需要另行形成经产品负责人确认的新版本，本评估不直接改写概要设计。

## 五、重点能力评估

### 5.1 公司分析

**可以稳定完成的部分：**

1. 用户输入和公司已有资产的结构化整理。
2. 公司官网、公开招聘页、公开新闻、融资事件、产品与业务方向、公开管理人员和办公地点的证据化汇总。
3. 将来源、访问时间、摘要和支持的结论绑定，无法访问时保留失败原因。
4. 让用户逐项确认后写入公司资产，并在新证据出现时生成更新建议。

**只能条件实现的部分：**

1. “正在招聘什么”“招聘难度如何”“哪些部门扩张或收缩”只能从公开岗位、新闻和人员变化推断。
2. 组织架构、上下游、合作、竞争和人才流动需要多来源交叉验证；单一来源不能自动写成确定关系。
3. 潜在联系人是否真实负责招聘、是否仍在职、是否能影响岗位，通常需要猎头确认。

**达到预期效果的产品条件：**每个关键结论都显示证据、时间和确定程度；没有可靠信息时明确显示“未找到 / 待核实”，不能用概括性文本填满页面。公司调研的价值应以“减少猎头研究时间并提高下一步判断质量”衡量，而不是以字段填满率衡量。

### 5.2 岗位分析

**可以稳定完成的部分：**从 JD、补充说明、公司资料和用户反馈中提取岗位定位、职责、关键技能、软性与隐性要求、关键词、风险和结构化差异。当前 Hunter 已有岗位输出 Schema、字段白名单、技能长度限制、来源要求、JD 更新开关和业务校验，可作为 SaaS 实现基础。

**需要验证的部分：**

1. 招聘难度不是 JD 的固有字段，应由人才供给、地点、薪资、角色稀缺性、公司吸引力和历史漏斗共同支持。
2. 建议挖猎公司和找人步骤需要可解释理由，不能只由模型凭常识生成。
3. 隐性要求和“岗位可能有坑”属于推断，应标记为建议或待核实，不能直接改写原始 JD 事实。

阶段一可以先给出“难度等级 + 影响因素 + 建议步骤”，并在真实招聘推进数据积累后校准；不应宣称是准确的招聘周期或成功概率预测。

### 5.3 人才关系与联系路径

关系可分为三档：

1. **强证据关系：**共同论文、共同专利、同一项目明确署名、用户手工确认。可以直接展示，并保留来源和时间。
2. **条件关系：**同公司、同部门、任职时间重叠、公开活动共同出现。可以显示为“可能认识 / 经历重叠”，不能自动推导实际熟悉程度。
3. **探索关系：**上下级、实际汇报、好友、可引荐路径。除非有直接证据或用户确认，否则只能作为建议路径。

OpenAlex 能提供稳定作者 ID、作品、机构和年份，但官方也明确说明作者消歧和机构匹配存在已知错误；因此学术合作关系适合自动召回，不适合仅凭同名自动写入正式候选人关系。关系数据必须包含两端身份、关系类型、方向、来源、时间范围、置信度和确认状态。

联系路径的业务承诺应是“找到一条或多条有证据支持的可能联系路径”，不是“保证联系到目标人物”。手机号存在时仍可生成关系路径，因为猎头可能希望通过熟人提高回复率；只有邮箱不应被视为可直接联系成功。

### 5.4 岗位重点人才梳理

**系统内范围可行：**可从正式候选人、人物线索、知识图谱、论文、专利和历史匹配结果中召回，再通过角色适配门禁、条件降权和排序形成候选池。当前 Hunter 已有共享精排、角色硬拒绝、条件折扣、证据要求、缓存和 Schema 修正逻辑，说明核心评分链路已有验证基础。

**市场全量范围不可承诺：**公开网络只能找到可索引且允许访问的信息，无法覆盖未公开履历、封闭平台、最新组织变化和大量普通从业者。产品必须让用户看见：

1. 本轮使用了哪些来源和资产。
2. 每个来源召回多少、去重多少、身份不确定多少。
3. 已覆盖哪些公司、角色和方向，仍有哪些缺口。
4. 候选人资料变化后，哪些匹配结果被重新计算。

“重点人才”可以作为岗位资产的动态派生结果，支持表格和关系图切换；它不应被描述为某岗位在整个市场上的完整人才名单。

### 5.5 候选人信息补全

**适合补全的来源：**用户上传简历和附件、候选人已有资料、论文与专利、GitHub 等公开开发者资料、公司官网和公开网页。GitHub 和 OpenAlex 都有明确 API 与调用预算，适合通过受控工具查询；公开网页则需要搜索、抓取、缓存、退避和失败降级。

**最关键的风险是身份而不是字段解析。**同名、别名、中文拼音、机构改名和时间冲突都可能把他人信息合并进候选人。当前 Hunter 的 OpenAlex 补全已经使用名称、公司、学校、论文锚点、模型判断和代码安全门禁，这个方向正确，但 SaaS 还需要统一的身份判断合同：

1. 明确同一人的稳定锚点和冲突字段。
2. 高置信且无冲突才允许自动转为正式建议。
3. 疑似匹配必须提供并排证据和“不是同一人”处理。
4. 自动合并错误在验收样本中必须为零；无法判断时宁可不合并。
5. 每个补全字段保留来源和获知时间，候选人原始资料不被静默覆盖。

手机号、私人邮箱和求职意愿属于数据覆盖与合规风险最高的内容，不应作为信息补全的完成标准。候选人补全的合理完成标准是：在不错误合并人物的前提下，提高可核验的经历、成果、公开身份链接和匹配所需信息覆盖。

## 六、数据与技术前置条件

### 6.1 已有实现基础

Hunter 本地版已经存在以下可复用基础：公司和岗位 Agent 的结构化输出与来源要求、候选人补全工作流、OpenAlex 人物身份判断、岗位角色硬拒绝与条件降权、人岗精排、人才地图多格式导入导出，以及 Agent 输出 Schema 和有上限修正。本轮针对这些链路运行 `153` 项聚焦测试并全部通过。

这证明项目不需要从零验证“结构化 Agent、身份门禁和匹配门禁能否工作”，但不能证明 SaaS 面对真实公开网页、同名人物和跨行业岗位时已经达到业务质量。正式方案应复用已有代码判断与测试样本，同时重新验证云端并发、租户隔离、来源授权和真实数据效果。

### 6.2 产品效果所需合同

以下不是在产品详细设计中决定具体技术选型，而是实现产品效果不可缺少的合同：

1. **统一身份层：**人物、公司、岗位、论文、专利和外部来源使用稳定内部 ID；别名和来源标识只是匹配证据，不直接替代身份。
2. **证据与来源层：**关键事实和关系至少记录来源 URL / 文件、摘要、获取时间、支持对象和可访问状态。
3. **时间与有效性：**当前任职、关系、招聘信号和公司事件必须带时间；过期、冲突和更新有明确状态。
4. **版本与影响分析：**正式资产更新后只重算受影响的匹配、关系视图和知识图谱，不全量重跑，也不覆盖用户布局和备注。
5. **模型输出门禁：**提示词降低错误率，代码 Schema、字段白名单、证据、身份和写入规则决定是否准入。
6. **来源治理：**每个数据源明确许可、配额、并发、缓存、失败退避和替代来源；不能让 Agent 自行绕过受控工具。
7. **评估体系：**为公司、岗位、候选人、关系和匹配分别建立带人工标注的黄金集；不能只用“任务成功”衡量业务质量。
8. **运行可靠性：**长任务使用状态机、幂等键、检查点、局部重试和结果版本；等待用户或外部信息时释放计算资源。

底层可以先用关系型数据库保存权威资产、关系事实、来源和版本，再建立供 Agent 查询的关系投影。只有当多跳关系探索的规模和查询复杂度通过真实数据证明关系型方案明显不足时，再引入图数据库；不应在没有容量证据前让双数据库一致性成为阶段一前置风险。

## 七、验证方案与临时门禁

以下阈值是进入正式开发前的建议验证门禁，不是最终 SLA；团队可以根据样本重新调整，但不能取消验证。

| 能力              | 最小验证样本                                                    | 需要观察的结果                                                     |
| ----------------- | --------------------------------------------------------------- | ------------------------------------------------------------------ |
| 公司分析          | 30 家公司，覆盖上市公司、未上市公司、创业公司和公开信息较少公司 | 关键事实准确率、每条结论证据可访问率、未知率、过期率、猎头节省时间 |
| 岗位分析          | 50 份 JD，覆盖至少 10 个岗位族                                  | 字段准确率、建议可解释性、招聘难度一致性、对标公司有效率           |
| 候选人补全        | 100 人，刻意包含同名、别名、跨公司和学术重名                    | 错误合并率、待确认召回率、字段证据率、无结果时的正确降级           |
| 人才关系          | 200 条人工标注关系，覆盖共同成果、同公司重叠和疑似上下级        | 关系类型准确率、方向准确率、时间有效性、错误自动写入数             |
| 人岗匹配          | 30 个岗位及猎头人工排序结果                                     | 硬拒绝错误、条件降权合理性、Recall@K、nDCG、不同岗位族稳定性       |
| 岗位重点人才      | 10 个真实岗位，分别有和没有既有人才图谱                         | 来源覆盖、去重、身份不确定率、列表增量更新、猎头实际采纳率         |
| 四类 Agent / 任务 | 每类至少 20 次真实端到端运行                                    | 成功、降级、恢复、Schema 修正、证据完整、成本和持续时间分布        |

建议的临时质量底线：

1. 高置信自动写入事实在标注样本中的准确率不低于 `95%`。
2. 自动合并人物的错误数为 `0`；达不到就改为人工确认。
3. 关键结论必须有可查看证据；无证据的推断不能伪装成事实。
4. 非法结构、身份冲突和证据不足不得进入正式资产。
5. 允许返回“未找到可靠结果”；不得用模型补写未知事实提高完成率。

## 八、阶段一范围建议

### 8.1 可以直接进入架构和技术方案

租户与账号、统一资产 ID、文件与证据、任务和运行状态机、审核写入、版本与回收站、关系事实模型、模型与数据源路由、运营可观测和合规基础能力。

### 8.2 完成小规模验证后进入完整开发

公司分析、岗位招聘难度、建议挖猎公司、候选人补全、人才关系自动生成、岗位重点人才梳理、周期信号和增量关系同步。

### 8.3 只作为探索能力

市场人才全量覆盖、实时组织架构、私人联系方式补全、真实汇报关系、求职意愿判断和保证可用的联系人引荐路径。

## 九、合规与外部来源风险

公开信息并不等于可以无限制收集和长期使用。《个人信息保护法》要求目的明确、与目的直接相关、最小范围、信息质量和安全，并规定对已合法公开个人信息的处理仍应处于合理范围；对个人权益有重大影响时需要更严格处理。网络数据安全规则也要求使用自动化工具访问和收集网络数据前评估影响，不得干扰网络服务正常运行。

因此，正式技术方案必须同时评估数据来源条款、个人信息处理告知与权利、保存期限、删除、更正、审计、自动化决策解释和供应商委托处理。本文只识别产品与技术风险，不替代正式法律意见。
