# 原型阶段三：四类业务任务完整流程实施计划

> 2026-08-30 口径更新：本文中历史使用的“业务主线”“支线任务”和“工作”均不再作为用户可见分类。四类场景现在统一表现为“任务”，内部步骤表现为“相关处理”或运行；正式路由为 `#/tasks/:taskId`。详细边界见 `docs/unified-task-model.md`。

> 状态：2026-08-20 已通过人类审批并冻结；阶段二已冻结，阶段四尚未开始。
>
> 日期：2026-08-20。

## 一、阶段目标

本阶段在阶段二已审批的统一对话、执行计划、内部任务、授权、等待、恢复和审核框架上，分别完成客户开发、岗位招聘、人才摸排和候选人求职四条业务主线。验收重点不是展示四段不同文案，而是证明四类业务可以使用同一交互框架承载不同输入、过程成果、外部等待、人工决定、正式资产写入和结束条件。

阶段三不重新设计导航、工作台、统一“新建工作”、支线任务和信号中心，不提前实现阶段四、阶段五的完整资产管理页面。业务主线中出现的资产详情与审核只覆盖继续当前流程所需的信息；完整资产管理仍按后续阶段交付。

## 二、共享页面结构

四类业务主线继续使用 `#/workstreams/:workstreamId`：

1. 左侧为可收起的业务主线历史；四条示例主线均可直接切换。
2. 中间为唯一主要工作区，包括主线头部、渐进对话、常驻执行计划和对话输入区。
3. 右侧详情区只在用户主动打开中量结果时出现；关闭后回到原对话位置。左右审核布局使用明确的主从关系：左侧当前行有选中强调和指向右侧的 SVG，右侧详情宽于左侧列表并显示详情类型标题。
4. 大量且必须审核的结果临时占用主要工作区，审核结束后返回原主线，不新开浏览器标签页。
5. 普通 Agent 回复使用 Markdown；表格审核、授权选择、等待状态、任务状态和大型结果由 Hunter 受控组件渲染。
6. 每条主线从第一条用户输入或继承的信号开始逐步显示，不能在首次打开时预装完整对话。

## 三、四条主线剧本

### 3.1 客户开发：星澜机器人招聘合作

**入口与输入**

- 路由：`#/workstreams/client-xinglan`。
- 来源：融资和团队扩张信号、星澜机器人官网招聘变化、用户已有行业关系。
- 用户目标：判断公司是否值得开发，找到招聘负责人和可用联系方式；有真实招聘需求时形成招聘机会，但不直接创建正式岗位。

**渐进过程**

1. 核验公司身份、融资和招聘变化，分别显示支持证据、反对证据、时效和不确定项。
2. 形成公司资料建议、正式联系人和联系人线索。摘要必须明确联系人总数、具备可用联系方式的人数、首选对象和仍缺失的信息。阶段一结构化联系方式只支持手机和邮箱；系统外获得的信息只作为普通跟进记录，不保存通信渠道类型。
3. 用户打开联系人审核，在当前工作区检查姓名、角色、公司关系、手机、邮箱、来源和身份可信度；用户可以修改选择或用自然语言反馈。
4. 公司与联系人写入确认完成后，Hunter 生成业务合作邮件草稿。用户可以修改收件人、发送身份、主题和正文，每次确认后才能发送；第一阶段不提供邮件自动发送授权。
5. 用户允许后进入“等待外部”，不显示运行动画，不持续消耗用量；用户可以补充线下回复。
6. 收到回复后形成招聘机会，展示需求摘要、确认依据、联系人、招聘方向和缺口。
7. 收到完整 JD 时只形成岗位草稿；用户确认后才创建正式岗位并建立岗位招聘主线。

**关键分支**

- 信号证据不足：保留信号并说明还需要什么，不创建公司外的新业务资产。
- 没有可用联系人：说明已尝试路径和缺口，可以建立寻找联系路径的支线，也可以等待用户关系补充。
- 联系无回复：停在等待外部并显示下次检查安排。
- 对方明确无需求：保存沟通结论并终止主线。
- 发现真实需求但信息不完整：创建招聘机会，不伪造正式岗位。

### 3.2 岗位招聘：具身智能 VLA 算法负责人

**入口与输入**

- 路由：`#/workstreams/position-vla`。
- 来源：星澜机器人正式岗位、JD、岗位解析、客户补充要求和本轮渠道边界。
- 用户目标：持续找到、筛选和推进合适候选人，本轮先交付不超过 20 位值得判断的人选，不直接联系。

**渐进过程**

1. 展示岗位理解、硬要求、软性和隐性要求、风险、寻访关键词及本轮找人边界。
2. 云端并行处理系统候选人、公开网络、论文专利和人才版图；认证人才平台只通过用户主动选择的本地任务处理，云端不登录或控制平台。
3. 云端与本机结果按批次持续汇入。每批人物线索立即完成身份判断、资料补全、去重、合并、角色硬门槛和最新岗位匹配，再增量进入候选人审核。
4. 审核显示完整资料、综合与分项得分、推荐理由、风险、证据和建议动作；结构化选择与自然语言指令均只建立岗位储备关系。
5. 审核结束后可以询问需要发邮件的人选；每次发送前必须确认收件人、发件人、主题、正文和附件，自动执行模式不能绕过。
6. 邮件发送后进入低频等待。收到回复或简历后更新候选人，只重做受影响的去重、补全和匹配步骤。
7. 正式推荐、面试、谈薪、Offer 和入职由猎头手动处理并记录，Agent 不自动改变推进阶段。

**关键分支**

- 本机协作不可用：云端来源继续处理，已有结果保留；用户可稍后在本机继续或下载本地任务。
- 本机任务使用旧岗位版本：仍接收返回结果，但按最新岗位重新匹配。
- 身份或字段冲突：进入合并审核，不静默覆盖或重复创建。
- 单一渠道失败：可以重试该任务，不把整条主线判为失败。
- 用户补充新要求：只调整受影响计划和候选人范围。
- 候选人未回复：等待外部；不重复消耗用量。
- 岗位关闭或用户终止：主线结束，不以找到或入职人数自动结束。

### 3.3 人才摸排：具身智能核心人才版图

**入口与输入**

- 路由：`#/workstreams/mapping-embodied`。
- 来源：用户给出的具身智能 VLA、机器人学习与灵巧操作范围，已有公司名单、论文、链接和组织资料。
- 用户目标：摸清目标公司、组织方向、关键角色、人物和关系，形成可复用的人才版图，并明确还缺什么、下一步做什么。

**渐进过程**

1. Hunter 复述目标和已知范围，形成可调整的摸排目标清单，不用未知市场总人数计算百分比。
2. 分批产生公司与生态、组织与方向、人物与角色、人物关系和联系路径；每批结果带来源和观察时间。
3. 身份明确且通过门禁的内容按授权增量写入人才版图；身份或关系不确定的内容进入待确认成果，不由自动流程直接写入。用户查看证据后可以明确确认写入，系统保留确认人、确认时间和原始不确定信息；结构与安全门禁仍不可绕过。交互只显示当前状态和一个下一步动作：待确认时提供“确认并写入”，确认后提供“撤销确认”，不并列展示两个互斥按钮。
4. 本批次审核固定使用“公司与组织”“人物与关系”“冲突与待补充”三个业务标签，默认进入“公司与组织”。Agent 只能把变化归入既有标签，不能动态新增、改名或排序标签。每个标签左侧显示本批次发生的具体变化，用户点击变化项后，右侧显示该变化影响的对象、关系、证据和写入状态。关系图是变化详情，不作为独立入口，也不要求用户先理解或选择图的类型。
5. 关系数据必须保留对象类型、关系类型、方向、时间、确认状态和证据。后续 Agent 可以从任意业务资产沿关系继续探索，并用原始关系路径解释结论；画布坐标只是前端布局，不作为 Agent 探索依据。
6. 系统可根据变化内容调用组织与方向、公司生态、方向与角色、人物关系、人才流动、联系路径和学术脉络等关系投影，但这些投影只在对应变化项中出现。关系图中的节点、连线、右侧详情和待确认状态保持联动；同一项关系在人物变化或冲突项中确认后，其他引用位置必须立即显示同一决定。
7. 每批更新后说明“已经摸清什么、还缺什么、下一步动作是什么、执行后预计得到什么”。
8. 用户随时补充文件、链接、截图或人物线索，只重做受影响范围。
9. 发现新公司、招聘需求或人物动向时形成信号；确有独立边界时建议支线，不无限递归启动任务。
10. 本次目标清单全部完成或剩余缺口被用户接受后结束本轮摸排；人才版图资产本身不进入“初版完成”或“维护中”状态。

**关键分支**

- 组织关系证据冲突：显示不同来源和时间，等待用户选择，不静默覆盖；用户可以明确确认其中一种判断并写入。
- 关键人物缺失：展示“待补充信息与下一步”，并可创建有限的人物探索支线。
- 公开信息不足：保留未知，不用模型猜测组织上下级或人物关系。
- 用户补充内部名单：说明影响范围，只更新对应公司、组织和人物。
- 发现招聘信号：进入信号中心，默认不打断当前摸排。

### 3.4 候选人求职：林昊职业机会

**入口与输入**

- 路由：`#/workstreams/career-linhao`。
- 来源：林昊近期更新简历和公开动态的候选人动向信号；用户已手动确认启动主线。
- 用户目标：判断林昊与系统内有效岗位的匹配关系，辅助猎头本人联系并核实求职意愿；不搜索公开市场职位，不自动联系候选人。

**渐进过程**

1. 展示触发原因、证据强弱、候选人现有联系方式和资料新鲜度。
2. 与系统内有效岗位进行匹配，显示每个岗位的分数、推荐理由、风险、缺口和建议沟通要点。
3. 用户查看完整匹配结果，并通过自然语言决定优先了解哪些岗位；Hunter 不代替猎头联系。
4. 猎头自行联系后，在对话或候选人跟进记录中补充结果、文字、文件或新简历；普通跟进不要求选择通信渠道类型。
5. 新信息先形成档案变化和合并摘要，再只重做受影响的去重与岗位匹配。
6. 暂无回复时进入等待外部；明确暂无求职意愿时保存结论并完成。
7. 有意愿且存在合适岗位时，用户确认把候选人交给一个或多个岗位招聘主线；没有合适岗位时完成本轮，未来新岗位形成新信号。

**关键分支**

- 信号证据不足：说明判断依据，由用户决定是否继续，不自动结束。
- 候选人未回复：显示等待对象、开始时间和提醒安排。
- 候选人提供新简历：展示变化、合并和重匹配影响，不能静默覆盖。
- 有意愿但无岗位：结束本轮，不让主线无限等待。
- 同一候选人已有未结束求职主线：进入既有主线，不新建重复主线。

## 四、共享组件与专用组件边界

### 4.1 继续复用的产品级组件

1. `WorkstreamHistory`、`WorkstreamHeader`、`ConversationTimeline`。
2. `Composer`、`AuthorizationSelector`、`RuntimeBar`、`PlanList`、`InternalTaskList`。
3. `HunterMarkdown`、`UserMessage`、`StatusBadge`、`Toast`、`Modal`。
4. `ObjectInspector`、`DecisionRequest`、加载、空、错误和权限受限状态。

### 4.2 阶段三新增的受控业务组件

1. `ContactReviewWorkspace`：公司、角色、手机、邮箱、来源和身份可信度审核。
2. `CandidateReviewWorkspace` 扩展：入储备后继续承载联系范围与异步回复回流。
3. `TalentLandscapeUpdate`：公司、组织、人物、关系、来源、冲突、待补充信息与下一步；待确认内容支持用户明确确认写入。
4. `PositionMatchReview`：同一候选人与多个系统内岗位的完整匹配比较。
5. `ExternalWaitState`：等待对象、开始时间、最近检查和下一次处理安排；Hunter 发送的邮件另行保留邮件状态。
6. `EmailDraftReview`：可编辑收件人、发件身份、主题和正文，并在本次确认后发送。

招聘机会、证据摘要、目标清单和少量比较结果不再建立场景专用卡片，由 `HunterMarkdown` 根据实际内容动态渲染；只有数据量大、需要选择、写入或产生外部影响时才进入上述受控组件。

这些组件只接收代码校验后的结构化数据。Agent 普通回复仍是 Markdown，不能输出任意组件、HTML 或 CSS。

## 五、状态与 URL 设计

每条主线路由支持以下通用状态，用于直接验收：

- 无参数：从第一条输入自动渐进演示完整正常路径。
- `?state=loading`：主线数据加载中。
- `?state=stream-error`：流式回复中断，保留已有内容并允许继续。
- `?state=limited`：平台或权限受限，只暂停受影响任务。
- `?state=waiting`：直接进入该主线的关键外部等待状态。
- `?state=error`：关键业务步骤失败，显示局部重试、补充信息或终止方式。

专用状态：

- 客户开发 `?state=no-contact`、`?state=reply`。
- 岗位招聘 `?state=review`、`?state=no-candidate`、`?state=candidate-reply`。
- 人才摸排 `?state=conflict`、`?state=gaps`。
- 候选人求职 `?state=no-position`、`?state=new-resume`。

URL 状态用于验收，不代表正式产品依赖查询参数保存业务事实；正常交互中的状态仍由页面操作和 Mock 数据联动产生。

## 六、响应式要求

1. 桌面端保留可收起主线历史、主要对话区和按需详情区。
2. iPad 优先保留对话和运行栏，主线历史改为覆盖式面板；大型审核使用完整主区域。
3. iPhone 使用全屏工作区，主线历史和详情均采用可返回覆盖层；授权、计划和输入区不能相互遮挡。
4. 表格在移动端改为分组列表，不出现横向滚动条；重要身份、状态、分数和操作不能因折叠消失。
5. 最小可见字号不低于 `12px`，正文优先使用 `14px` 及以上；标签文字不得换行或被截成半个字。

## 七、实施顺序

1. 冻结阶段二审批状态并建立阶段三剧本、交互覆盖和组件边界。
2. 抽取现有岗位招聘工作区的公共外壳，不改变已审批交互。
3. 扩展岗位招聘完整后半程，验证公共外壳没有回归。
4. 实现客户开发、联系人审核、对外授权、等待和招聘机会结果。
5. 实现人才摸排的分批成果、冲突审核、待补充信息与下一步、用户确认写入和信号分流。
6. 实现候选人求职的系统内岗位匹配、人工联系、资料回流和重匹配。
7. 补齐通用与专用异常状态、移动端等价交互和页面刷新恢复。
8. 完成格式、构建、全量 Playwright、截图对比和线上真实页面检查。

## 八、审批门禁

1. 四条主线的目标、输入、过程成果、人工节点、等待和结束条件可以一眼区分。
2. 四条主线均从第一条输入渐进推进，不一次显示完整对话。
3. 主线内部任务、独立支线、信号和正式资产边界没有混用。
4. 所有正式写入、对外操作和高风险业务动作符合已确认授权边界。
5. 外部等待不显示持续运行，不持续消耗用量；新信息只重做受影响步骤。
6. 正常、loading、empty、error、permission-limited、流式中断、等待和恢复均可实际操作。
7. 桌面、iPad、iPhone 无横向溢出、遮挡、原生默认控件和不可理解的技术输出。
8. 全量测试和截图 Review 通过后，才提交阶段三审批；审批前不进入阶段四。

## 九、实施与 Review 结果

1. 四类业务主线均使用同一对话、执行计划、相关任务、授权、等待和恢复框架，但分别实现了独立输入、过程成果、人工节点和结束条件。
2. 客户开发完成招聘信号、公司联系人审核、邮件草稿编辑与逐次确认、外部等待和招聘机会回流；无联系人时展示已尝试路径和可执行缺口。
3. 岗位招聘补齐云端与本机结果持续合并、岗位储备后的邮件确认、外部等待、新简历合并、局部重匹配和无候选人结果。
