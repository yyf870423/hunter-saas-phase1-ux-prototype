# 原型阶段二：自动化通用交互框架实施计划

> 状态：2026-08-20 已通过人类审批并冻结；2026-08-30 经人类确认，用户侧对象统一为“任务”。一步完成、持续推进和内部步骤只影响执行方式，不形成用户可见类型。统一边界见 `docs/unified-task-model.md`。
>
> 日期：2026-08-19。

## 一、阶段目标

本阶段验证 Hunter 能否使用一套稳定交互承载不可预先穷举的 Agent 任务，不提前完成四类业务任务的完整业务剧本。阶段二使用“具身智能 VLA 算法负责人”这一岗位招聘示例，贯通用户输入、流式回复、动态计划、内部运行、过程结果、等待用户、审核和继续执行。

## 二、页面与路由

| 页面     | 路由              | 主要内容                                         | 页面关系                             |
| -------- | ----------------- | ------------------------------------------------ | ------------------------------------ |
| 新建任务 | `#/new`           | 自然语言输入、附件、授权模式和执行计划判断       | 一步完成，或进入持续任务区           |
| 任务列表 | `#/tasks`         | 状态分类、搜索、分页、创建与删除                 | 所有用户任务使用同一列表             |
| 任务区   | `#/tasks/:taskId` | 任务历史、对话、计划、相关处理、检查区和审核区   | 由工作台、导航、通知或新建入口进入   |
| 信号中心 | `#/signals`       | 紧凑信号流、状态分类、搜索、批量处理、详情检查区 | 信号可观察、忽略、失效或转化为新任务 |

### 统一创建入口规则

1. 用户只输入目标，不在创建前或创建后选择、识别“业务主线”“支线任务”或其他内部分类。用户侧统一称为“任务”。
2. 可以立即完成的任务在当前对话直接返回结果，保留任务记录，但不生成没有必要的执行计划。
3. 需要多阶段推进、等待外部回复、持续更新资产或编排多个步骤的任务保留长期上下文。一步完成和持续推进都进入同一任务列表和任务区。
4. Hunter 可以说明执行计划、等待点和结束条件，但不向用户输出系统内部生命周期名称。任务规模不是唯一判断条件。
5. 目标存在关键歧义时，只追问一个当前必要问题。用户可以直接用自然语言纠正执行计划和持续范围。
6. 编排层保留任务运行、任务步骤运行、资产 AI 运行和系统运行的恢复与资源边界；这些范围只用于系统调度、运营诊断和成本治理。
7. 信号转化时只需选择“启动新任务”或“关联现有任务”。任务的具体执行方式由 Hunter 判断。

## 三、统一任务区布局

1. 左侧为可收起的任务历史，承载搜索、置顶、新建、状态和历史定位。所有任务使用同一视觉层级。
2. 中间为主要对话区。用户输入使用右侧边框容器；Hunter 使用全宽 Markdown，不使用头像和聊天气泡。
3. Agent 对话正文只输出 Markdown。标题、段落、列表、引用、表格和链接由统一渲染器展示；Agent 不生成 HTML、CSS 或带产品样式的业务组件。
4. 输入区支持文字、文件、截图和直接粘贴链接；`Enter` 发送，`Shift + Enter` 换行。
5. 输入区下方显示“仅分析、执行前确认、自动执行”三种授权模式，切换只影响尚未执行的动作。
6. 执行计划和内部运行使用输入框上方的常驻运行栏，默认收起并可随时展开；不再把执行计划混入对话历史。展开区域限制高度，不能长期挤压对话区。
7. 执行计划在任务运行期间持续更新。每一步明确显示待开始、进行中、完成、等待用户、已暂停或需调整，并标明对应的用户要求；已经完成的步骤保留完成标记。
8. 新信息导致计划变化时，展开区使用紧凑调整摘要说明变化，并直接更新受影响步骤；只重做受影响范围。
9. 执行计划展开区直接显示单列步骤，不设置“计划依据”或其他二级切换。相关处理只显示状态汇总，展开后才显示具体运行，不能再与计划左右平铺。
10. 中等信息在当前页右侧检查区显示；大量候选人审核临时使用主工作区，不新开浏览器 Tab。
11. 必须操作的大型结果由 Hunter 使用受控审核组件渲染；对话正文只给出 Markdown 摘要和一个标准入口。
12. 候选人审核底部使用全宽批量处理区，明确已选人数、未选候选人去向及不会自动联系的边界。勾选后只执行“加入岗位储备”，未勾选即表示本轮不处理。联系候选人是审核后的主线动作，不作为另一种审核去向。
13. 页面刷新恢复对话位置、输入草稿、计划展开状态、检查区和未提交审核状态。

## 四、渐进式示例

1. 首次进入只显示用户第一条输入，不预装完整对话。
2. Hunter 立即给出真实流式反馈，随后形成可收起的动态计划。
3. 内部步骤可以并行运行，过程状态在运行栏更新；普通步骤不生成通知。
4. 少量证据直接在对话内表格显示；单个对象或大型结果在右侧检查区显示。
5. 候选人集合形成后，Hunter 暂停并等待用户决定；在用户处理前不继续外部联系。
6. 用户可以打开完整审核，也可以输入“将 85 分以上的人加入岗位储备，但不要选择赵星羽”等自然语言筛选规则。
7. 两种入口生成同一审核结果，并反馈已加入岗位储备、本轮未处理和需要补充信息的数量。

## 五、任务、资产 AI、运行与信号边界

1. 任务内部步骤和运行只在所属任务的运行栏或检查区出现，不进入全局任务列表，避免执行条目淹没用户真正关心的任务。
2. 用户从全局入口提出的目标进入统一任务列表；详情复用相同的对话、动态计划、结果和授权协议，不向普通用户暴露内部生命周期类型或技术信息。
3. 从资产详情发起的确定性 AI 处理留在当前资产，不创建任务。推荐报告同样在岗位匹配详情内持续修改并保留文件版本。
4. 信号不是任务。信号中心保存待判断变化，可观察、忽略、失效或转化，并保留来源和转化去向。
5. 重复信号合并来源和最近变化；信号不提供常规删除，不进入回收站。

## 六、公共组件扩展

本阶段先在公共组件层新增，再由业务页面组合：

1. `ConversationTimeline`、`UserMessage`、`HunterMarkdown`、`StreamingReply`。
2. `Composer`、`AttachmentChip`、`AuthorizationSelector`。
3. `RuntimeBar`、`PlanList`、`InternalTaskList`。
4. `HunterMarkdown` 承载普通分析、证据摘要和少量结果；`ObjectInspector` 仅承载需要独立查看的大型结果。旧的 `ArtifactRenderer`、`EvidenceTable` 不再作为对话协议组件。
5. `DecisionRequest`、`ReviewWorkspace`、`CandidateReviewTable`。
6. `TaskHistory`、`TaskList`、`SignalFeed`、`SignalInspector`。现有原型内部组件名可暂时保留 `Work*`，但不能影响用户文案和后续产品模型。

## 七、状态与异常门禁

1. 覆盖 normal、loading、empty、error、disabled、permission-limited。
2. 区分等待用户、等待外部、已暂停、重试中和失败；等待状态不显示持续运行，也不持续消耗用量。
3. 流式失败保留已完成内容并允许从检查点继续，不重复显示内容。
4. 未识别只读结果降级为通用文档，不显示原始 JSON；涉及写入或授权时必须阻止。
5. 删除任务前说明停止的运行、保留的正式资产和无法撤销的外部动作；删除进入回收站 30 天。
6. 信号转化和审核提交必须防重复点击，超时先查询实际状态。

## 八、审批门禁

1. 用户只需理解“任务、资产 AI、运行、信号”四层对象；内部执行差异不形成额外导航和列表。
2. 对话、计划、相关处理、检查区和大型审核区层级清楚。
3. 从第一条用户输入开始渐进推进，不一次显示完整历史。
4. 自然语言和结构化审核产生一致数据变化。
5. 桌面、iPad 和 iPhone 均无横向溢出，最小可见字号不低于 `12px`。
6. 所有按钮、输入、筛选、Modal、Drawer、暂停、恢复、重试、终止、删除和错误状态可实际操作。
7. Playwright E2E、控制台错误检查和关键页面截图全部通过后，才提交阶段二审批。

## 九、实现与 Review 结论

1. 阶段二页面和公共组件已经按本文件范围实现，入口统一收敛在 `#/review`。
2. 业务主线从第一条用户输入渐进推进，流式回复、动态计划、内部任务、证据、候选人审核和继续执行不会一次性预装。
3. 输入草稿、当前阶段、运行栏展开状态、检查区和未提交候选人审核在页面刷新后恢复；加载、流式中断和平台权限受限均提供局部恢复动作。
4. 候选人审核支持分层、关键词、匹配分排序、逐项详情、批量选择、结构化决定和自然语言决定；两种入口复用同一业务语义。
5. 移动端可以完成主线输入、候选人详情检查、支线任务和信号详情处理，不以隐藏关键详情换取版面适配。
6. 本阶段只证明通用框架可用，不代表客户开发、岗位招聘、人才摸排和候选人求职四类完整业务剧本已经完成；完整分支属于阶段三。
7. 构建、格式检查、Playwright 全量回归、控制台错误检查、横向溢出检查和桌面/iPad/iPhone 截图门禁全部通过后方可发布审批版本。
8. 信号中心桌面端使用左窄右宽布局，信号列表负责定位，详情区获得主要阅读空间；移动端继续使用列表进入全屏详情的交互。
9. 信号中心桌面端采用明确的主从关系：左侧使用次级背景承载选择列表，选中项通过层级和方向标识连接右侧；右侧作为主要详情画布，并在切换信号时更新“所选信号”内容。
10. 2026-08-20 第一轮人类验收提出的动态计划、移除支线技术信息和信号页比例三项修改均已完成；全量 `48` 项 Playwright 测试通过。
11. 第二轮反馈已完成：主线与支线计划统一常驻输入框上方；计划步骤显示对应用户要求，调整记录显示补充原文、受影响步骤和不变边界；信号中心采用明确的“左侧信号列表 → 右侧所选信号详情”主从结构。
12. 第二轮专项构建、交互和截图测试共 `19` 项通过；格式检查、生产构建和全量 `48` 项 Playwright 回归通过，桌面、iPad 和 iPhone 截图未发现遮挡、溢出或层级问题。GitHub Pages 部署及线上关键文案校验通过。
13. 第三轮反馈已完成：执行计划改为单列并渐进披露计划依据和相关任务；候选人审核明确批量作用范围和实际处理结果；Agent 与支线普通回复改为 Markdown；桌面设置入口并入用户菜单。格式检查、生产构建、全量 `49` 项 Playwright 测试和关键截图复核通过。
14. 第四轮反馈已完成：候选人审核取消“切换处理方式 + 确认”组合，改为三个直接业务动作；主线和支线执行计划统一使用“计划步骤 / 计划依据”同区标签切换；后续验收交付必须包含全部页面、异常状态 URL 和交互进入步骤。格式检查、生产构建、全量 `49` 项 Playwright 测试和关键截图复核通过。
15. 第五轮反馈已完成：候选人审核移除“本轮排除”，只保留两个直接业务动作；执行计划移除“计划依据”及二级切换；主线和支线的计划箭头方向统一互换。格式检查、生产构建、专项 `19` 项和全量 `49` 项 Playwright 测试及关键截图复核通过。
16. 候选人审核语义进一步收敛为单一“加入岗位储备”。“加入联系名单”被移除，联系范围由审核完成后的业务主线继续询问或接受自然语言指令；结构化选择和自然语言筛选均先建立岗位储备关系。专项 `15` 项和全量 `49` 项 Playwright 测试及候选人审核截图复核通过。
17. 公共对话输入框取消原生手动缩放，改为随内容自动增高；到达最大高度后只在输入框内部滚动，清空或发送后恢复初始高度。该规则同时作用于业务主线、支线任务和新建工作区。生产构建、自动高度专项测试、全量 `50` 项 Playwright 测试和展开状态截图复核通过。
18. 新建入口收敛为 `#/new`，任务列表和任务详情统一使用 `#/tasks` 与 `#/tasks/:taskId`；原型尚未进入开发，不保留旧入口兼容。
19. 统一新建工作页已覆盖直接完成、独立支线任务、业务主线、目标歧义、判断失败和权限受限。格式检查、生产构建、全量 `53` 项 Playwright 测试和桌面/iPhone 关键截图复核通过。
20. 2026-08-26 信息架构曾收敛为统一“工作”；该结论已被 2026-08-30 的统一任务模型替代。
21. 2026-08-30 用户侧导航、列表、历史栏、详情路由和新建结果统一使用“任务”；`#/tasks` 和 `#/tasks/:taskId` 成为正式入口。一步完成任务仍保留记录但不生成空计划；资产页 AI 处理和推荐报告不进入任务列表；运行范围只用于所属对象和运营诊断。
