# 任务本次操作确认原型

## 已确认决定与范围

2026-11-24用户要求不再手动输入“确认”，随后批准文案细化：“同意，推送原型并更新详细设计”。只更新并推送原型、原位同步正式详细设计；不改AROS 1420、SDK、后端、数据库或正式官网。用户补充要求先同步最新详细设计，不能用旧本地副本覆盖。

完整规则见[文案合同](task-approval-copy-spec-20261124.md)。确认的是当前具体业务操作，不是永久授权Agent。

## 组件与交互

- 公共TaskExecutionApproval复用Button、StatusBadge、图标及工作台token。execution-approval-copy.js维护合法动作、标题、主次按钮和只读选择类型，未知动作、无范围、缺回调或非法模式不可执行。
- 摘要依次展示对象/范围、真实变化及去向、依据/缺口/边界。储备示例新增顾言川1位，林昊、周明远、陈楚宁3位保持原阶段；赵星羽排除，不能称新增4人。
- 单资产、储备/推进、导入与匹配、联系人、组织梳理、跟进安排/记录/取消和周期计划均使用具体业务按钮；邮件独立“确认发送”，不继承一次写入确认。
- 只读联系人核实是“继续核实联系人/暂不继续”的业务选择，仅分析也能继续，不因此保存联系人、发送邮件或切换模式。
- 周期计划明确持续运行、可暂停/调整，显示浏览器时间显示时区；仅本地模拟保存。生产需持久化明确时区、旧新配置和实际下次时间，不能依赖浏览器默认值完成调度合同。
- 同请求提交锁防双击，失败保留范围。对象、输入、附件、版本、权限与模式变化重新核对；未发送内容先发送/清空，点击不能吞掉输入。
- 点击显示“已点击：具体动作”，本地领域消息保存并校验结构化决定事件；自然语言历史保留原文，不把“是”改写成“确认”。

## 后端接入要求（本轮未实现）

1. 服务端下发approval_request_id、任务/轮次、合法动作、稳定对象ID集合、草稿/结果/计划/资产版本、逐项差异、去向、可执行性和失效原因。
2. 按钮与自然语言决定走同一受控执行边界，检查身份、权限、结构、证据、版本及幂等。原型的本地请求键与有限解析不等于生产审批API，不能把按钮简单接到任意“确认”文字。
3. 受理、处理中、完成、失败、部分成功和未知分别返回。未知先查询回执，不盲目重放写入/邮件；部分成功只恢复安全失败项，并回读真实资产。
4. 单资产首次与后续修改、身份冲突、资料审核、邮件逐封确认和高风险删除门禁不变；一次确认不切换任务模式。
5. 运行时代码校验字段、类型、合法动作和请求归属；不能只靠提示词。确认事件、业务原文与事实依据分别保存。
