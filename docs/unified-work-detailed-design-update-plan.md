# 统一“工作”后的详细设计更新计划

> 状态：2026-08-26 已完成在线详细设计更新与交叉 Review。

## 一、调整背景

用户通过同一个自然语言入口创建工作，不需要在创建前选择“业务主线”或“支线任务”，查看时也不应再学习两套列表、详情和状态。产品统一使用“工作”作为用户可见、可管理的业务过程；持续周期、一次性交付和内部拆分只作为系统编排差异。

运营端仍需要查看底层执行记录，但采用“工作执行、相关任务执行、系统后台任务”三类技术运行口径，并通过“所属工作”回到用户可见对象。

## 二、文档结构判断

详细设计继续保留 `00—13` 的编号，不增加新文档，也不调整后续资产、设置和运营端编号。原 `01—03` 的职责仍然需要分别存在，但名称和边界调整为：

1. `01 工作、执行与资产关系`：定义用户工作、系统执行和正式资产的统一关系。
2. `02 工作`：定义统一创建、工作列表、对话式详情、计划、等待、恢复，以及四类业务场景的完整流程。
3. `03 工作执行与恢复`：定义工作执行、相关任务执行、系统后台任务的拆分、生命周期、恢复、递归和运营追溯；不再定义用户侧独立支线列表。

## 四、必须保持不变的边界

1. 四类业务场景的目标、正常路径、异常路径、资产演进和人工节点不删除，只取消用户必须理解的“业务主线类型”前置分类。
2. 业务资产的数据结构、列表、详情、审核、版本、来源、合并、删除和恢复规则不重新设计。
3. 用户侧仍可在工作内查看执行计划和相关任务状态；统一工作不等于隐藏执行过程。
4. 运营端“任务与故障”继续存在，用于技术运行、错误聚合和安全恢复，不成为用户端第二套工作管理入口。
5. 自动执行只改变动作是否需要逐次确认，不关闭 Hunter 强制门禁。

## 五、交叉 Review 门禁

1. 用户侧文档不再要求用户选择、识别或管理“业务主线/支线任务”。
2. 所有旧 `/tasks` 原型入口改为统一 `/works` 或对应工作详情；兼容路由不作为正式入口写入文档。
3. 设置、通知、订阅和数据删除文案与已部署原型一致。
4. 运营端三类执行名称、所属工作字段和恢复逻辑与 Mock 数据一致。
5. 资产文档能够从正式资产追溯到工作和执行，但不复制工作状态或执行状态。
6. 文档编号、相互引用、原型 URL、关键状态截图和在线标题保持一致。

## 六、实际更新结果

1. 详细设计继续使用 `00—13` 编号，没有新增文档，也没有调整资产、设置和运营端文档编号。
2. `01—03` 已按统一工作模型重构为：
   - `01 工作、执行与资产关系`
   - `02 工作`
   - `03 工作执行与恢复`
3. 用户侧只保留“工作”这一种可见、可创建和可管理的对象；用户不再选择或识别“业务主线”“支线任务”。
4. 系统内部保留“工作执行”“相关任务执行”“系统后台任务”三类执行记录。相关任务执行在所属工作中查看，系统后台任务仅在运营端管理。
5. 工作台已统一为“工作、相关执行摘要、机会与信号、行动事项”的信息层级，不提供第二套全局任务列表。
6. 设置中心已统一为“所有新工作”的默认自动化授权；运行中的工作可以单独调整，已有工作不因默认值变化而自动改变。
7. 运营端“任务与故障”已覆盖三类执行，并通过“所属工作”追溯用户可见对象；安全恢复不会创建第二条用户可见工作。
8. `04—09` 只更新术语、引用和入口，没有改变业务资产的数据结构、生命周期和已审批交互。
9. `11` 只同步账号认证与统一工作模型的关系，没有改变公开首页和认证流程。

## 八、最终 Review 结论

1. `00—13` 在线文档中不存在旧 `/workstreams`、`/tasks` 原型入口。
2. 在线文档中不存在要求用户选择或管理“业务主线”“支线任务”的旧口径。
3. 所有在线文档没有重复标题；所有图片均有有效资源；所有表格均保留显式列宽。
4. `01—03` 的在线标题、职责和相互引用一致，`12—13` 与设置及运营端原型一致。
5. “输入版本”等少量执行技术概念继续保留，用于恢复和追溯，不作为用户侧独立对象或入口。
6. 本轮没有修改原型代码，也没有重新设计业务资产；更新范围与本计划一致，无已知阻塞问题。
