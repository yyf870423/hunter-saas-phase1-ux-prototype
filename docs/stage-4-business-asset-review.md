## 一、对照依据

本轮没有沿用旧 SaaS 原型中的资产页面，而是交叉对照以下四类依据：

1. 已通过人类审批的《Hunter 阶段一目标业务对象与字段基线》及其交叉 Review。
2. 已通过人类审批的《Hunter 阶段一产品信息架构：页面清单与关系矩阵》。
3. 已冻结的阶段一至阶段三原型、Markdown-first 对话协议和云端配套本机能力边界。
4. 当前 Hunter 的真实数据库、公司服务、候选人、岗位、论文、专利、人才地图、匹配和招聘推进页面。

当前 Hunter 只作为现状和已验证交互参考；与已审批目标基线冲突时，以目标基线和最新原型决策为准。

## 三、本轮发现并修正的问题

### 3.1 联系方式口径发生过版本冲突

较早的候选人和联系人字段基线允许微信及其他结构化联系方式；阶段三审批后，最新口径已经收紧为阶段一结构化联系方式只支持手机和邮箱。

本轮已统一修正为：

1. 候选人和联系人结构化联系方式均只保存手机和邮箱。
2. 电话、线下、微信和其他联系结果可以通过人工备注或人工补录沟通记录回流。
3. 阶段一云端系统直接发送与读取的沟通渠道只设计邮件。

### 3.2 第一版遗漏了人物线索和共享沟通的数据边界

人物线索不是正式资产，但承担论文、专利、人才版图和候选人身份确认之间的缓冲；共享沟通承担异步回复回流。缺少它们会迫使系统过早创建候选人，或在多个页面复制同一条消息。

本轮已增加人物线索、组织单元和真实沟通三个必要支撑对象，并明确它们不占用正式资产总集。

### 3.3 招聘机会与岗位的基数不应无依据扩展

第一版关系矩阵曾把招聘机会—岗位写为多对多。已审批业务只要求一条机会拆分多个岗位，且岗位保存来源机会即可满足阶段一。

本轮调整为：一条招聘机会可以形成多个岗位，一个岗位最多有一个来源招聘机会。已有岗位尚无来源机会时允许关联；同一岗位被多个机会重复指向时，先处理机会重复或由用户选择来源，不扩展多来源结构。

### 3.4 候选人原始简历文本不能丢失

当前 Hunter 的 `raw_text` 参与全文搜索和匹配，且用户已经确认仅命中原始简历内容时需要明确说明。本轮已将解析后的原始文本纳入简历版本结构：参与搜索和匹配，但页面没有对应字段时不伪造展示位置。

### 3.5 反向列表不能成为第二个编辑入口

当前 Hunter 的公司关联候选人同时包含字符串匹配和手动补关联，关系含义容易漂移。本轮已增加“每类关系只有一个事实所有者”规则：

1. 公司任职人才来自候选人工作经历。
2. 公司岗位来自岗位公司关系。
3. 公司联系人来自联系人—公司关系。
4. 公司招聘推进来自候选人 × 岗位推进。

反向列表可以发起纠错，但必须修改原始事实，不能创建公司侧补丁。

### 3.6 岗位资料与匹配判断必须版本化

当前 Hunter 已有 JD 解析、条件快照和角色门禁，但岗位 Agent 分析、客户确认要求和历史匹配的关系仍不够清楚。本轮已统一：

1. 已确认招聘要求才可作为硬约束。
2. 岗位分析和寻访关键词是建议，不自动成为硬要求。
3. 匹配结果关联候选人、岗位和匹配策略版本。
4. 资料变化只让旧结果过期，不自动删除结果或移出已有推进。

### 3.7 岗位推进与匹配结果不能继续使用低密度旧交互

岗位详情原型曾使用“移动阶段”按钮、小样本匹配列表和相近的状态标签，不能承载上百位候选人，也无法让用户快速区分硬门槛、角色适配和实际推进状态。本轮统一修正为：

1. 候选人流程使用有稳定分类背景色的横向泳道，卡片直接拖拽并在落位前补充可选备注。
2. 岗位级自定义阶段可以拖拽排序；当前 Hunter 已验证的储备和四类终态保持锁定，不能改名、删除或调整顺序。
3. 候选人完整推进记录和备注时间线从泳道卡片直接打开，并使用右侧抽屉承载可能很长的时间线；泳道提供常驻横向滚动控件，不再依赖阶段移动按钮承载详情。
4. 匹配结果使用分类 Tab、分页列表和右侧详情工作区，默认按分数倒序；匹配分、硬门槛、有条件匹配、未匹配和已移除使用不同结构和视觉层级。
5. 已进入岗位流程的候选人用与泳道稳定分类一致的颜色标签显示当前阶段；未匹配候选人不伪造分数，硬门槛拒绝候选人不能加入岗位流程。
6. 从结果移除和标记不合适都进入“已移除”，用户可以恢复；该操作不删除候选人档案。
7. 推荐报告从流程中候选人发起为独立支线任务，允许用户持续通过自然语言和文件要求 Agent 修改，但不会自动发送给客户。报告交付为可在线查看和下载的 Markdown 文件；匹配详情只保存最新文件，任务对话保留历史版本并支持重新生成。

### 3.8 岗位历史版本必须提供恢复依据

仅显示版本号、修改时间和“恢复”按钮不足以支持用户判断。本轮已经统一为：岗位 JD 历史版本使用左侧版本列表和右侧完整内容预览，用户选择旧版本后先阅读当时全文，再执行恢复；恢复生成新版本，不覆盖历史。来源招聘机会并入岗位基本资料的关联字段，不再单独占据一整行。

## 四、关系所有权 Review

| 用户看到的页面     | 读取的唯一事实                 | 禁止的重复维护                           |
| ------------------ | ------------------------------ | ---------------------------------------- |
| 公司—任职人才      | 候选人工作经历中的正式公司关系 | 公司详情单独增加“关联候选人”事实         |
| 公司—招聘推进      | 公司岗位下的候选人 × 岗位推进  | 公司详情另存一套阶段和备注               |
| 候选人—岗位匹配    | 带版本的人岗匹配结果           | 候选人和岗位分别保存不同分数             |
| 候选人—岗位流程    | 唯一推进关系和阶段历史         | 失败后重新创建第二条推进关系             |
| 联系人—候选人      | 同一自然人的身份关系           | 把联系人档案并入候选人或反向复制完整资料 |
| 人才版图—正式资产  | 正式资产引用加当前版图上下文   | 在版图中复制完整候选人、公司或成果档案   |
| 论文或专利—人物    | 原始署名加人物身份关系         | 只凭姓名直接关联候选人或批量创建人物线索 |
| 时间线中的真实消息 | 共享沟通记录                   | 在联系人、候选人和主线中分别复制消息     |

结论：当前模型能够支持从不同入口查看同一业务事实，同时避免多处编辑造成数据漂移。

## 五、生命周期 Review

### 5.1 正式资产

1. 公司、联系人、候选人、论文和专利不增加业务生命周期状态。
2. 人才版图只区分正常和已删除，目标清单表达摸排进展。
3. 岗位使用招聘中、已暂停和已关闭。
4. 招聘机会使用跟进中、已完成和已关闭。
5. 八类资产删除后统一进入回收站 30 天。

### 5.2 过程与建议

1. 待确认、冲突、过期和门禁失败是建议或资料状态，不是正式资产状态。
2. Agent 排队、运行、等待、失败和完成是任务状态，不写入资产生命周期。
3. 候选人的储备、推进中、已入职和失败属于岗位推进关系，不是候选人状态。
4. 论文和专利没有跟进中、已完成等招聘状态。

结论：没有发现把任务状态、审核状态和业务资产状态混用的已知问题。

## 六、原型验证结论

1. **候选人合并**：使用摘要、字段级选择和关系保留说明，不要求用户并排阅读两份完整档案；无变化也有明确反馈。
2. **公司关联**：公司页只显示反向关系，纠错返回原始事实所有者；不恢复字符串动态关联作为第二套事实。
3. **联系人双重身份**：联系人保留多公司关系，候选人同人关系独立展示和审核，没有把联系人列表变成简历列表。
4. **招聘机会拆岗位**：详情明确区分方向、创建岗位与机会自身状态，支持创建新岗位或关联尚无来源机会的已有岗位。
5. **岗位资料层级**：岗位资料、候选人流程、匹配结果和相关工作分为四个 Tab；JD、已确认要求、Agent 分析和版本在岗位资料内分组。
6. **人才版图复杂关系**：公司生态、组织方向、人物关系与学术路径分别投影；关系详情和来源在同一工作区查看。
7. **成果人物身份**：论文和专利使用同一身份审核边界，只有姓名相同不会直接建立正式关系。审核以单个人物为单位，点击谁只审核谁；Modal 只给出一位疑似候选人，并按联系方式、工作经历、教育经历、项目与研究经历展示来源人物与候选人的完整记录和一致性判断，不使用表格压缩多条经历。两侧经历数量可以不同，分别显示数量并标识无法对应或由候选人资料补充的记录，不伪造一一对应关系。Modal 不一次展示整篇成果的全部作者或发明人，也不允许改选其他候选人。关联、保留线索和暂不关联均为点击即处理的独立动作。
8. **回收站恢复**：普通恢复、身份冲突和永久删除均有独立确认与失败反馈。

以上结论均已映射到 `docs/stage-4-interaction-coverage.md` 和 Playwright 用例。

## 七、留给技术方案的实现问题

以下问题不由产品原型提前决定：

1. 正式资产、子记录、关系、来源、证据和变更使用哪些数据库表或服务。
2. 人才版图关系使用关系数据库、图数据库或混合投影。
3. 候选人合并的事务、并发、撤销和跨关系完整性实现。
4. 公司识别、联系人身份、论文作者和专利发明人的自动判定阈值。
5. 文件内容指纹、对象存储、引用计数和物理清理方式。
6. 资料版本、搜索索引、缓存和旧结果过期的具体实现。
7. 沟通渠道同步、幂等、轮询、Webhook 和失败恢复方式。

技术方案必须满足本轮定义的用户可见效果和强制门禁，不能以实现方便为理由退回字符串动态关联、静默覆盖或级联删除。

## 八、Review 结论

最终交叉 Review 未发现阻塞人类验收的已知矛盾。业务资产模型、字段字典、六批原型、交互覆盖和测试结果已保持一致；阶段一至阶段三原型的既有流程仍通过全量测试。

当前可以进入人类验收。人类审批前不把阶段四标记为冻结，也不进入生产开发。
