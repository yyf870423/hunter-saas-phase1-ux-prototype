# 专题图谱重构对概要设计、详细设计与原型的影响梳理

> 状态：影响分析已完成，“专题图谱”名称已确认；尚未修改在线概要设计、在线详细设计或正式原型。
>
> 依据：2026-08-31 已确认的《摸排能力重构讨论记录》、当前 Hunter 真实代码与历史样本、现有 SaaS 概要设计、详细设计及阶段四原型。

## 一、结论

本次变化不是简单增加一种关系图，而是重新明确“摸排、专题图谱、共享关系和业务结果”的边界：

1. **摸排是任务或业务过程，不是资产。**
2. **专题图谱是承载一个或多个关系图页的正式业务资产。** 每个图页允许用户按自己的理解整理自由文本、层级、顺序、布局、备注和关系，并可在画布与层级表格之间切换，不强制限定为公司组织架构。
3. **专题图谱可以按需关联正式资产。** 每个节点可以不关联资产，也可以关联一个或多个公司、候选人、人物线索、联系人、招聘机会、岗位、论文或专利。
4. **专题图谱由用户先创建，再通过三种路径维护内容。** 顶层图谱不能由文件或 Agent 静默创建；已有图谱内的图页可以人工维护、文件导入，也可以由 Agent 生成或更新，三种方式使用同一份图谱模型。
5. **图谱本地内容、共享事实、来源业务关联和来源派生关系按所有者分开。** 图谱本地文字、布局和备注由图谱维护；共享关系保存用户确认或能够独立核实且没有其他天然所有者的事实；人岗匹配、岗位流程、论文作者等由原业务资产维护；前同事、共同作者、共同发明人等可以由来源记录派生。同一语义关系同时存在来源推导和独立人工证据时合并展示证据，但不能复制成图谱自己的可编辑关系数据。
6. **Agent 可以读取整张专题图谱。** 图谱既是用户可维护的成果，也是后续岗位找人、人物关系分析、联系路径和工作空间查询的重要输入。
7. **岗位人才梳理、联系路径、公司关系和学术关系不是专题图谱的附属页面。** 它们读取共享事实或专题图谱，但各自在岗位、人物、公司和学术资产中保留稳定业务入口。
8. **同一图页的两种展示共用页面级内容，不同图页的节点实例彼此独立。** 画布与层级表格共用该图页的节点实例、图谱本地关系和资产关联；不同图页分别保存节点实例、层级与布局，但共同引用正式资产、共享关系、来源业务关联及其派生关系。阶段一不把组织树、人物关系和公司生态预设为额外固定视图。
9. **正式资产名称确定为“专题图谱”。** “人才摸排”继续表示任务或业务过程，两者不混用。
10. **一份专题图谱可以包含多个图页。** 图页保存不同内容范围、展示方式和布局，但复用同一套正式资产、共享关系、来源业务关联及其派生关系。
11. **具有长期业务价值的关系持续可查询并可复用。** 共享事实由其关系记录维护；来源业务关联由原资产维护；前同事、共同作者、共同发明人、人才流动等派生关系根据来源持续计算或建立可追溯索引。用户有独立证据时仍可补充同类共享关系，界面合并展示证据并按来源纠正，不能把派生结果复制成第二条可独立编辑的关系。
12. **正式资产共享，节点实例独立。** 同一资产可以在多个图页或多个位置显示；每个节点实例可以有独立名称、备注和布局，删除节点实例不删除正式资产或其他引用。
13. **同一图页支持切换展示方式。** 阶段一至少提供画布视图和类似 Excel 合并单元格的层级表格视图，两者共用底层内容并分别保存布局配置。
14. **层级表格按父子结构自动合并。** 用户通过调整节点层级和顺序改变表格，不支持无法映射回画布的任意单元格合并。
15. **层级与交叉关系分开表达。** 表格使用关系摘要和详情承载交叉关系，画布使用连线承载；两者引用同一份图谱本地关系、共享关系或来源业务关联且不复制节点。
16. **每个节点实例只有一个主要父节点。** 主要父节点负责层级和表格结构，交叉关系不改变层级；同一正式资产可以通过多个节点实例出现在不同分支。
17. **节点点击先进入统一详情面板。** 面板承载节点本地内容、多个资产关联、交叉关系、来源和最近变化，再由用户打开具体正式资产。
18. **Agent 新写入不能静默改图，来源同步不重复审核。** Agent 提出的图谱、资产或共享关系变更继续使用三档授权并形成变更批次；已经在来源资产中合法生效的数据同步到图谱只是实时引用更新，不再次触发 Agent 授权。
19. **人工编辑采用自动保存与成组版本。** 当前操作可撤销和重做，连续操作合并为历史记录；Agent 与导入始终形成独立版本。该规则作为阶段一暂定方案，待原型验证。
20. **专题图谱需要覆盖完整操作体系。** 图谱、图页、节点、关系、画布、层级表格、Agent、版本和异常恢复分别建立操作清单，不把图谱降级为只读关系图。
21. **画布采用“位置自由、结构受控”。** 用户可以自由拖动节点坐标；普通拖动不改变层级，自动布局只整理坐标与路径且可以撤销，系统不得静默重排用户布局。
22. **自由节点可以创建并关联正式资产。** 阶段一暂定复用对应资产已有的完整表单、查重、身份确认和写入门禁，并使用可返回原图页和原节点的应用内全屏创建工作区，不默认打开新的浏览器 Tab；具体返回体验待高保真原型验证。
23. **阶段一支持有限的节点批量操作。** 用户可以整体移动位置、移动到其他图页、批量挂到新的父节点、移动包含父节点的完整分支，以及删除节点实例；批量操作必须显示影响范围、阻止循环层级并支持整体撤销，不批量创建资产或确认共享关系。
24. **人工关系与 Agent 关系使用不同确认依据。** 用户在两个正式资产之间手动保存允许由图谱维护的共享关系时，该操作本身视为人工确认并形成共享关系；自由节点或“其他关系”只保存在当前图谱。论文作者、人岗匹配、岗位流程等来源业务关联仍回到对应资产维护。前同事、共同作者等来源派生结果不能从图谱直接改写，但用户有独立证据时可以补充同类共享关系并与派生证据合并展示。Agent 产生的关系遵守授权模式、证据和写入门禁，不能自动提升为共享事实。
25. **共享关系需要统一去重与冲突处理。** 相同对象、类型、方向且范围和时间重叠的关系复用原记录并补充证据；不同范围或时间可以并存；无法解释的真正冲突进入对比确认。移除图谱引用和删除共享关系事实是两种不同操作。
26. **文件只能导入已有专题图谱的图页。** 用户先创建顶层图谱，再在图谱内完成格式校验、结构预览、重名处理和写入；导入不能创建另一份专题图谱，也不能静默合并到当前图页。
27. **文件结构按来源分区映射为图页。** 单一结构文件生成一个图页；Excel 的每个有效数据 Sheet 分别生成图页；同一结构中的多个根节点保留在同一图页。用户可以在导入预览中选择要写入的部分。
28. **导入格式不能相对当前 Hunter 缩水。** SaaS 阶段一继续支持 EdrawMind/WPS、XMind、OPML、Markdown、FreeMind、Hunter JSON 和 Excel；底层实现可以重构，但需要逐格式校验结构和信息退化提示。专题图谱详情中的业务导出范围和交互暂不设计，后续单独确认；站内层级表格不等同于文件导出。全产品的数据可携带和灾备恢复要求不因此取消。
29. **外部文件不依赖 Hunter 资产 ID。** 图页结构先完整保留，AI 再结合节点及上下文识别资产并判断高可信唯一匹配；只有姓名不能自动关联。代码承担候选范围、结构和最低证据门禁，歧义进入确认，未命中保持自由节点，识别失败不回滚图页。
30. **AI 分析属于导入后台处理，不是独立任务。** 导入确认页默认开启“智能分析节点与连线关系”，用户可以关闭；图页先落地，AI 再识别资产并尝试理解无标签连线，过程在导入记录中显示并允许暂停、继续或重新分析。
31. **无标签连线默认只是图谱本地结构连接。** 仅凭位置和连接方式形成的语义只能作为建议；存在明确文字或外部证据时，才按授权模式和共享关系门禁处理。无法判断不会阻塞导入，也不会制造大量强制审核项。
32. **智能分析使用就地标记与集中审核双入口。** 节点或连线标记用于发现问题，分析审核模式用于集中处理和完整对比；两者与画布、层级表格之间必须实现选择定位、处理状态和数量的实时联动。
33. **分析标记按处理需要保留。** 待确认、冲突和失败持续显示；自动处理只在本批次短期提示；正常关联不长期显示 AI 标记。完整判断依据和撤销能力保留在分析记录与历史版本中。
34. **创建顶层图谱后不自动生成空白图页。** 用户进入合法的空图谱后，再选择新建空白图页、导入图页或让 Agent 生成图页；三种路径可以在同一图谱中混合使用，不形成不同图谱类型。
35. **图谱内 Agent 操作不进入全局任务列表。** 它复用任务的对话、计划、进度、授权和恢复组件，记录归属于专题图谱；只有从全局入口发起时才形成正式任务。两条路径使用同一能力与门禁，并通过唯一变更批次避免重复写入。
36. **图谱内 AI 使用全屏双区协作工作区。** 左侧显示对话、计划、状态和业务可读过程，右侧显示更大的图谱与变更预览，并支持双向定位和收起对话。过程展示不暴露原始工具事件、内部命令或模型隐藏推理。
37. **统一资产内 AI 协作工作区作为暂定方向。** 候选人、岗位、公司、论文、专利等资产可以复用同一全屏协作外壳，右侧按资产展示字段变化、证据、结构化结果或文件；需要通过跨资产高保真原型验证后才能替换当前交互。改造前原型回滚基线为提交 `26bee0039a58a0f291580e95a6cd07ddca08c6e7`。
38. **专题图谱是正式资产与共享关系的实时视图。** 已关联资产的摘要和已引用共享关系发生变化时，所有对应图谱自动同步，不形成长期积压的待处理批次；同步不覆盖用户本地节点文字、备注、层级和布局，历史版本仍保留当时状态。
39. **资产内派生或阶段性关联也需要实时同步。** 人岗匹配、岗位流程、资产归属、论文作者等关系继续由原资产或业务记录管理，图谱只保存来源引用和展示配置；来源状态变化时自动刷新对应连线与标签，不复制成脱离来源的共享事实。
40. **自动同步包含新增节点。** 已有引用、与图中节点产生了允许展示的新关系、保存的内容范围命中，或从图谱上下文产生并绑定回图谱时，都属于自动同步范围；新关系的一端不在图页时也直接增加节点和关系，不能只显示提示等待用户手动处理。名称相似但没有正式关系的数据不能被加入。
41. **图谱版本不能回滚来源事实。** 历史版本可以展示当时使用的来源状态，但恢复图谱只恢复图谱本地内容和引用配置；正式资产、共享关系和来源业务记录继续使用当前有效状态。
42. **自动更新以证据充分或用户确认为前提。** 已合法生效的数据直接同步；疑似、证据不足或身份冲突的变化只进入待确认展示层，并通过图上标记、通知和待处理事项提醒用户。待确认内容不参与正式统计、匹配或关系查询，确认后才写入数据所有者并转为正式图谱内容。
43. **自动新增不无限递归。** 新节点加入后，只同步本次变化直接涉及的关系，以及图页明确关注的关系类型或内容范围；不能因此把该节点的全部论文、共同作者、历史公司和其他外围网络级联加入。后续单独命中范围的关系仍实时同步。
44. **用户删除形成节点实例或关系级排除。** 自动加入的节点或关系被用户从当前图页删除后，同一自动加入依据不能反复把它加回来；排除不删除底层数据，也不影响同一资产在当前或其他图页中的其他节点实例。原节点以隐藏状态保留本地内容和布局，只能通过撤销或“隐藏内容”恢复；用户在其他上下文仍可创建引用同一资产的新节点实例。
45. **来源失效时先移除关系，再判断节点。** 纯自动加入、没有用户维护且没有其他有效关系的节点自动进入隐藏内容；用户编辑、移动、调整层级、备注过，或仍有其他有效关系的节点继续保留，并标记原关联已经失效。
46. **同一变化更新全部命中图页。** 同一资产或关系出现在多个图页时，所有符合各自内容范围的图页都同步最新来源状态；各图页仍独立保留布局和隐藏规则，通知在专题图谱层聚合而不是逐页重复发送。
47. **通知按影响分级并聚合。** 普通字段和低影响数值变化只更新图谱及历史；新增或移除节点、关键关系、来源失效和影响业务判断的变化发送聚合通知；需要用户介入的问题同时生成待处理事项。
48. **自动新增采用局部布局，用户可以一键整理。** 新节点靠近触发关系的节点，批量新增形成整齐分组，空间不足时进入相邻新内容区域；系统不重排整张图。用户可以一键整理当前图页，也可以只整理选中分支，整理只改变坐标和连线路径并支持撤销。
49. **搜索定位和画布视口属于基础能力。** 搜索默认覆盖整份专题图谱，以下拉列表展示全部匹配并优先排列当前图页结果；结果按照“图页名 + 节点名”显示并补充层级路径。选择结果后自动切换图页、展开必要祖先并将目标置于屏幕中心。普通搜索不返回已经进入“隐藏内容”的节点，遵循可见即所得；隐藏节点只能从专门入口恢复。画布支持单节点及全部展开/收起、放大、缩小、恢复 `100%`、自适应全部内容和聚焦选中内容，不提供固定节点。
50. **画布使用语义缩放和统一的长文本处理。** 缩小时保留节点标题、资产类型和风险状态，逐步隐藏备注、数量等次要信息；放大后恢复。任何缩放比例下的过长文字都要截断并使用产品自定义 Tooltip 展示完整内容，不能撑破节点或使用系统原生提示。
51. **每个图页独立保存并恢复最近视口。** 图页分别保存平移位置、缩放比例和展开状态，切换或返回时恢复；搜索定位可以临时居中目标，但不会影响其他图页的视口状态。

因此，当前详细设计确实需要调整，但不需要全部推倒重写。影响可以分为“大改 1 篇、中等修改 6 篇、小改 5 篇、当前无需修改 2 篇”。

## 二、为什么现有设计需要变化

### 2.1 当前 Hunter 已经验证了强类型地图不适用

当前 Hunter 曾把节点限定为“部门 / 人物”，但真实的 22 份地图、1857 个节点中，约 45% 的节点无法可靠归为部门或人物。实际内容同时包含：

1. 公司和团队组织架构。
2. 候选人追踪和人才名单。
3. 招聘需求和岗位方向。
4. 产品线、业务方向和上下游关系。
5. 用户自行整理的专题树和人物关系。

Hunter v0.10.0 已把底层改为“多根自由文本树 + 人物关联”。这说明用户的使用方式不是误用，而是在填补系统缺少的自由关系整理空间。

### 2.2 当前 SaaS 详细设计仍然偏向固定的结构化摸排成果

现有 SaaS 设计虽然已经不把人才版图只理解为组织架构，但仍存在以下限制：

1. 新建版图默认要求“摸排目标和已知范围”，没有提供先创建空白顶层图谱、再通过人工维护、导入图页或 Agent 生成图页完善内容的路径。
2. 版图详情主要围绕固定的公司生态、组织方向、人物关系和审核视图组织。
3. 节点和关系默认倾向于被解释为结构化事实，没有明确允许长期存在的图谱本地自由节点和自由连线。
4. 创建目标、覆盖缺口和完成标准被默认用于所有地图，不适合用户导入“技术上下游”等不以完整摸排为目的的内容。
5. 现有原型中，地图详情和 Agent 结果的关系较强，但手工持续维护自由树的能力不足。

### 2.3 当前 Hunter 前端和底层本身也存在口径不一致

当前 Hunter 后端已经支持多根自由树，但前端仍把一级根节点称为“公司 Tab”，并使用“添加公司”等文案。用户实际可以把一级根节点用于公司、技术方向、产品线或其他专题，因此该文案已经不能准确表达底层能力。

SaaS 版不能继续把“一级根节点 = 公司”固化为新系统规则。

## 三、概要设计影响

### 3.1 需要受控复核，但现在不直接修改

概要设计属于已经审批的上位文档，不能因为详细设计讨论直接改写。本轮只记录需要复核的具体位置：

1. **核心产品对象**：当前把人才版图定义为“目标范围、组织节点、方向、角色、关键人、关系、缺口、覆盖和证据”。需要评估是否补充“自由画布内容、按需资产关联和多种创建方式”。
2. **过程成果与正式资产边界**：需要明确图谱本地自由内容可以是正式专题图谱资产的一部分，但不等于已经确认的全局业务事实。
3. **产品能力架构**：需要补充 Agent 可以把专题图谱作为工作空间数据读取和分析，并按用户要求形成受控表格、树图和关系图。
4. **完整业务流程**：当前“人才摸排形成组织和关系成果”的方向仍成立，只需判断是否补充“摸排可以更新已有专题图谱，也可以只形成岗位人才梳理、联系路径或一次查询结果”。
5. **信息架构**：专题图谱仍属于业务资产，不新增共享关系层独立导航。

### 3.2 不应改动的概要设计原则

1. 摸排仍是猎头完整业务流程中的重要能力。
2. 原始输入、过程成果、证据和确认结果都需要保留。
3. 用户确认或自动确认与 Hunter 强制门禁仍然决定正式写入。
4. 专题图谱仍服务客户开发、岗位招聘和候选人经营。
5. 工作空间、权限、证据、身份和数据隔离边界不变。

### 3.3 概要设计处理门禁

只有在专题图谱详细设计和原型完成并确认后，才对概要设计做一次最小、受控的口径更新。更新前需列出逐条差异并由产品负责人确认，不能随详细设计自动修改。

## 七、数据结构和后续技术方案需要面对的变化

本节只说明产品效果对技术方案提出的要求，不在产品阶段指定数据库或实现技术。

1. 需要保存专题图谱、图页、自由节点实例、自由连线、布局和版本。
2. 需要支持一份专题图谱包含多个图页；图页保存范围和布局，并允许同一底层对象出现在多个图页。
3. 同一图页的画布和层级表格视图需要复用底层内容，并分别保存画布布局和表格展示配置。
4. 节点与正式资产是多对多关系，允许零关联和多关联。
5. 同一正式资产的不同节点实例需要分别保存上下文显示名称、备注、图页位置和布局，同时引用同一份正式资产资料。
6. 图谱本地自由连线和共享关系事实必须可以区分，不能共用一条无范围的关系记录。
7. 共享关系需要支持人物、公司、组织、论文、专利等不同对象，并保留方向、范围、时间、来源和可信状态。
8. 图谱对人岗匹配、岗位流程、岗位归属、论文作者等来源业务关联，以及前同事、共同作者、共同发明人和人才流动等来源派生关系，需要保存稳定引用和展示配置，不能复制出第二个业务所有者；来源变化后必须定位并自动更新全部受影响图谱和图页。
9. 岗位人才梳理需要保存当前结果、历史版本和候选人资料引用，并支持输入变化后的自动影响识别、增量重算和当前结果更新。
10. 联系路径需要保存历史结果、证据、状态和失效原因，并在底层关系变化后自动更新当前路径状态和可替代路径。
11. 来源同步与 Agent 写入必须区分：来源中已合法生效的数据更新图谱不重复授权；Agent 新建或修改正式事实仍受授权和门禁。
12. Agent 需要受控读取专题图谱、共享关系、来源业务关联和来源派生关系，并把查询结果交给固定的表格、树图、关系图和文件渲染器。
13. 技术方案需要评估关系型数据库、图查询能力或组合方案，但产品详细设计不预先指定必须使用图数据库。
14. 技术方案需要提供可解释的影响定位机制，覆盖显式引用、图中节点产生的新关系、保存的内容范围和图谱上下文绑定；不能依赖名称模糊匹配决定向哪些图谱写入变化。新关系的一端不在图页时，需要自动创建节点实例并使用稳定布局规则放置，同时避免重排用户现有画布。
15. 图谱历史版本需要保存可追溯的来源快照或来源版本引用，同时保证“恢复图谱”和“恢复来源资产”是两套独立操作，不能通过图谱恢复复活已经删除或失效的业务数据。
16. 技术方案需要把正式同步与待确认分析层分开：正式同步更新当前引用；待确认层保存候选变化、证据、判断依据和处理状态，并与图上标记、通知和待处理事项使用同一事项标识完成去重和状态联动。
17. 自动传播需要带有明确的关系深度和内容范围门禁。一次来源变化只传播直接命中的对象和关系，不能因为新节点被加入而递归遍历并写入其完整关系网络。
18. 图页需要保存节点实例级和关系级排除记录，并记录对应自动加入依据，自动同步写入前先检查排除状态；隐藏节点保留本地文字、层级和布局，来源资料在隐藏期间继续更新。立即撤销或从隐藏内容恢复时复用原节点实例并取消排除；用户在不同层级或上下文明确添加同一资产时可以创建新实例，不能被隐藏实例错误阻止。排除记录随图页删除而清理，但不能影响底层资产、其他节点实例或其他图页。
19. 节点实例需要记录自动加入依据、用户是否编辑、移动或调整层级、当前有效关系数量和最近失效原因，以支持来源失效后的确定性处理。自动隐藏是图页状态变化，不得删除历史版本或底层资产。
20. 影响定位和同步执行需要覆盖一份专题图谱中的全部命中图页，并保证同一来源版本在各图页一致；图页布局、节点位置和排除规则分别应用。多图页变化共用一个图谱级变更批次和聚合通知。
21. 变化事件需要携带影响等级、图谱、图页、对象和变化类型，支持按时间与类型聚合通知；低影响变化仍写入可查询历史。通知与待处理事项引用同一变化记录，避免状态重复和处理结果不一致。
22. 搜索索引不能只覆盖当前图页或当前已经渲染的节点，需要覆盖整份专题图谱并优先返回当前图页结果。结果数据至少包含图页名、节点名、层级路径和命中内容；查询时必须排除图页级隐藏节点。定位其他图页结果时，需要切换图页、展开目标祖先路径、恢复必要节点并把目标移动到视口中心。缩放、展开、收起、自适应和一键整理需要在大图渐进加载下保持结果一致。
23. 画布渲染器需要支持语义缩放，并为节点标题、备注、关系说明等可变长度文字统一提供截断检测和产品自定义 Tooltip。不同缩放级别的显示规则必须可预测，不能通过任意缩小字体规避溢出，也不能依赖浏览器原生 `title` 提示。
24. 图页视图配置需要独立保存平移坐标、缩放比例和展开状态，并区分正常恢复与搜索定位、自适应、聚焦选中等主动视口变更。跨图页定位不能覆盖其他图页的视图配置。

### 7.1 进入技术方案前必须完成的可行性验证

以下内容不改变产品结论，但会直接影响架构选型、研发工作量和阶段一交付风险，不能等到编码阶段再处理：

1. **图页模型与关系所有权**：验证页面级节点实例、图谱本地连线、共享关系、来源业务关联和来源派生关系可以在同一查询中组合，同时保持唯一所有者和可解释来源。
2. **变化传播与幂等**：验证一次资产或关系变化能够准确定位全部命中图页，完成去重、排除检查、局部布局、版本记录和聚合通知；重复事件不能制造重复节点或重复关系。
3. **派生关系更新**：验证任职、论文作者和专利发明人变化后，前同事、共同作者、共同发明人和人才流动等派生关系能够增量更新，并能追溯到来源记录。
4. **大图渲染与搜索**：使用真实数据分布和放大样本验证渐进加载、跨图页搜索、展开定位、语义缩放、画布与层级表格切换及移动 Web 操作。节点和关系规模目标需要在技术方案前确定。
5. **版本与恢复**：验证图谱本地版本、来源快照或版本引用、隐藏与排除状态可以独立恢复，且不会回滚正式资产或复活已经失效的来源关系。
6. **多格式导入**：为 7 类保留格式分别准备正常、损坏、超大、无标签连线、多根和多 Sheet 样本，验证格式门禁、结构保真、退化说明和失败不产生半成品图页。
7. **Agent 变更协议**：验证 Agent 能够输出受控的节点、关系和布局变化，代码可以检查范围、结构、身份、证据和重复；修正失败时保留原图谱并返回可理解错误。
8. **后台运行恢复**：验证实时同步、派生重算和岗位人才梳理增量更新失败后可以安全重试、恢复和排障，同时不进入用户任务列表，也不向运营端暴露业务正文。

## 八、明确不做的范围

1. 不建设 Miro、FigJam 级别的任意白板。
2. 不允许用户配置无限扩张的自定义关系类型。
3. 不新增抽象的“共享关系数据库”导航。
4. 不要求每个自由节点都成为正式资产或全局事实。
5. 不把一次 Agent 推断直接写成已确认关系。
6. 不因资产更新覆盖用户在地图中的文字、布局和备注。
7. 不要求每份地图都有覆盖率、完成标准或严格摸排目标。

## 九、交叉 Review 收敛结果

本轮按照“正式资产、共享关系、来源业务关联及其派生关系变化后，当前图谱必须自动保持最新”重新检查了此前全部决策，已收敛以下口径冲突：

| 检查项         | 原有矛盾或缺口                                                                 | 收敛后的统一规则                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 数据分层       | 曾把所有长期关系统称为共享关系事实，与来源业务关联由原资产维护冲突             | 统一为图谱本地内容、共享事实、来源所有内容三类所有权；来源所有内容包含业务关联及其派生关系。固定关系类型只统一词汇，不改变所有权。 |
| 图页与展示方式 | “整份图谱只有一份底层节点”与“不同图页可重复引用同一资产”相互冲突               | 同一图页的画布与层级表格共用页面级节点实例；不同图页的节点实例和本地连线彼此独立，只共同引用正式资产和来源关系。                   |
| 派生关系       | 前同事、共同作者和共同发明人既可能由来源记录计算，也可能来自用户掌握的独立证据 | 来源推导结果只回到来源纠正；独立证据可以补充共享关系。两者命中同一语义关系时合并展示证据，不重复统计或制造两个所有者。             |
| 图谱内新建关系 | “两端为正式资产即可形成共享关系”会误把论文作者、人岗匹配等来源关联写成通用关系 | 只有允许由图谱维护的共享关系可以直接保存；来源业务关联必须进入其原资产流程，保存后再实时同步回图谱。                               |
| 更新时机       | 旧口径中存在“标记待更新、之后集中处理”的可能                                   | 当前图谱自动同步或增量重算，不依赖用户再次启动 Agent，也不形成长期积压批次。                                                       |
| Agent 授权     | 来源同步可能被误解为一次新的 Agent 写入                                        | Agent 新建或修改事实继续受授权和门禁；来源中已合法生效的数据同步不重复审核。                                                       |
| 证据门槛       | “自动更新”可能被误解为把疑似关系直接写到当前图谱                               | 证据充分或用户确认的变化直接同步；疑似变化进入待确认展示层，并联动图上标记、通知和待处理事项。                                     |
| 图谱范围       | “更新所有相关图谱”缺少可执行边界，也可能让新对象只停留在提示中                 | 按显式引用、图中节点的新关系、保存的内容范围或图谱上下文绑定确定影响范围；命中后直接新增节点和关系，不按名称相似度猜测。           |
| 递归扩张       | 自动加入新节点后可能把其全部外围关系继续带入，造成图谱失控                     | 只传播本次直接关系和图页明确关注的范围；后续关系单独命中时再实时加入，不做无边界级联。                                             |
| 删除后重现     | 用户删除自动节点后，后续同步可能再次把同一内容加回来                           | 删除形成当前图页的节点级或关系级排除；底层数据保留，用户恢复后才重新参与自动同步。                                                 |
| 隐藏与多实例   | “再次添加同一资产必须恢复隐藏节点”与“同一资产允许多个节点实例”冲突             | 隐藏实例只通过撤销或隐藏内容恢复；普通搜索不返回隐藏节点。用户在其他上下文可以明确创建引用同一资产的新节点实例。                   |
| 来源失效       | 关系失效后直接删除节点会丢用户维护内容，全部保留又会留下无效信息               | 立即移除失效关系；纯自动且无其他价值的节点自动隐藏，已有用户维护或其他有效关系的节点保留并标记。                                   |
| 多图页一致性   | 只更新当前图页会让同一来源在其他图页继续显示旧状态                             | 更新全部命中图页，各图页独立保留布局和隐藏规则；变化记录和通知在专题图谱层聚合。                                                   |
| 通知泛滥       | 每次字段或分数变化都通知会淹没真正需要用户处理的问题                           | 低影响变化只记录；结构性和重要变化聚合通知；疑似、冲突和失败再进入待处理事项。                                                     |
| 历史恢复       | 历史版本保留旧状态，但未说明恢复是否会覆盖当前来源                             | 历史版本只用于追溯；恢复只恢复图谱本地内容和引用配置，不回滚正式资产或来源记录。                                                   |
| 导出范围       | 操作清单曾保留“导出当前图页或整图”，与最新暂缓决定冲突                         | 当前阶段只保留专题图谱业务导入设计，详情导出格式、范围和入口后续单独确认；全产品数据可携带和灾备要求不取消。                       |
| 报告与导出     | “专题市场报告是导出成果”可能被误解为已经承诺专题图谱文件导出                   | 专题市场报告是任务生成的成果文件；专题图谱数据导出仍然暂缓，两者不共用产品承诺。                                                   |
| 顶层图谱创建   | 任务或导入可能被理解为能够直接创建图谱                                         | 顶层专题图谱只由用户创建；文件和 Agent 只能在已有图谱中增加或更新图页。                                                            |
| 后台运行       | 原影响矩阵把执行恢复和运营端判断为完全无影响，遗漏实时同步失败和增量重算故障   | 任务列表不展示这些后台运行，但执行恢复和运营端需要补充幂等、重试、故障状态和脱敏运行元数据。                                       |

交叉 Review 后，两份当前决策文档内部没有发现仍会阻塞后续原型设计的产品口径矛盾。现有阶段三、阶段四、在线详细设计和原型尚未按本轮结论更新，因此“当前结论已收敛”不等于“全部产品资料已经一致”。仍需通过原型验证的内容是大图交互、动态新增内容的视觉落点、全屏资产内 AI 工作区和复杂审核效率，这些属于交互验证项，不改变本轮已经确认的数据所有权和实时同步原则。

## 十、建议的调整顺序

1. 完成本轮结论 Review，并冻结作为下一版原型的产品边界。
2. 更新本地业务资产模型、数据字典和统一任务/资产 AI 影响说明，不改在线概要设计。
3. 重做专题图谱原型，并同步补充候选人、岗位、公司、论文、专利、任务、信号和运营排障入口。
4. 用高保真原型验证多图页、画布与层级表格、大图搜索、实时变化、复杂审核和资产内 AI 协作；交互问题在原型阶段调整。
5. 原型审批后，将在线“08 人才版图”更名并重写为“08 专题图谱”，再按影响矩阵更新 01—10 和 13 中受影响的文档。
6. 对全部详细设计和概要设计做交叉 Review，确认没有职责重复或口径冲突。
7. 最后以逐条差异形式提请是否更新概要设计；未经确认不修改概要设计。

## 十一、与本次变化无关但已发现的既有口径问题

当前概要设计和部分在线详细设计仍使用“业务主线 / 支线任务 / 工作”，而最新原型已经统一为“任务”；部分旧内容仍提到本地寻访 App 协作，最新产品边界已经取消云端与该 App 的通信。这些问题不是人才版图重构造成的，不能混入本轮变化后归因于人才版图。

后续做全量文档交叉 Review 时需要单独处理，但本影响清单不借此扩大人才版图修改范围。
