# 候选人任职关系与入库后立即匹配原型方案

> 状态：原型已于 2026-09-02 通过产品验收。在线详细设计将在本次原型基线推送后统一回写。
>
> 制定时间：2026-09-02。

## 一、需要解决的问题

1. 候选人详情已经展示关联公司、学术成果和合作人，但无法直接找到当前或曾经同公司、同部门的系统候选人。
2. 上传候选人简历后，用户仍要进入候选人详情再次发起人岗匹配，入库和使用之间存在重复操作。
3. 上传或新建岗位后，用户仍要进入岗位详情再次发起人岗匹配，无法在创建时表达后续意图。
4. Agent 创建候选人或岗位时，如果不询问是否立即匹配，就会与手动上传和新建形成两套不同流程。

## 二、统一规则

### 2.1 候选人任职关系

1. 候选人详情的“关联信息”增加“同公司与同部门候选人”，不增加新的一级 Tab。
2. 同公司与同部门候选人、学术成果和合作人归入同一个“人物与成果关系”区域，通过二级 Tab 切换显示；一次只展示一种关系，避免三个长表格纵向堆叠。
3. 关系由候选人已经确认的工作经历派生，不要求用户运行新的 Agent，也不成为新的正式资产。
4. 表格支持搜索、关系类型筛选、公司筛选和分页，适应几十到上百条关系，不使用卡片平铺。
5. 关系类型至少包括：当前同部门、曾经同部门、当前同公司和曾经同公司。
6. 每条关系显示候选人、关系类型、共同公司与部门、任职重叠时间、对方当前职位、资料状态和详情入口。
7. 同部门必须有可核验的部门依据。部门缺失或只能判断同公司时，不能推断为同部门。
8. 工作经历、公司身份或部门信息变化后，派生关系自动刷新；证据不足时显示待确认，不静默写成确定关系。

### 2.2 入库后立即匹配

1. UI 统一命名为“写入后立即人岗匹配”，避免用户误以为文件上传完成就会绕过解析、查重和审核。
2. 默认关闭，避免批量导入时产生用户没有预期的模型用量。
3. 只有候选人或岗位成功新建、合并或更新后才启动匹配；待身份确认、写入失败和仅保留为线索的记录不启动。
4. 匹配异步运行。资产写入成功不被匹配失败回滚；失败后可以从资产详情的 AI 处理记录重试。
5. 同一候选人版本与岗位版本已有有效匹配结果时复用结果，不重复计算。

## 三、候选人上传交互

入口：`#/candidates/new?mode=upload`。

1. 在文件上传区下方增加“写入后立即人岗匹配”复选项。
2. 开启后显示匹配范围：
   - 全部招聘中岗位。
   - 指定岗位。
3. 选择“指定岗位”后显示可搜索多选下拉，至少提供岗位名称、公司和状态。
4. “上传并解析”后继续进入现有身份查重和字段变化审核，不提前运行匹配。
5. 审核页显示本次写入后的操作摘要。用户完成写入后，页面提示匹配已经启动，并可进入候选人“匹配与推进”查看进度。
6. 批量候选人导入使用一次批次级配置，不要求逐人选择。完成摘要分别显示新建、合并、待确认、写入失败、已启动匹配和未启动匹配数量。

## 四、岗位上传与新建交互

### 4.1 手动新建岗位

入口：`#/positions/new`。

1. 在创建操作前增加“创建后立即人岗匹配”复选项。
2. 开启后说明将使用新岗位的确认版本，与系统内可用候选人进行一次匹配。
3. 创建成功后进入岗位详情的“匹配结果”，显示运行中状态；关闭时仍进入岗位资料。

### 4.2 数据导入

入口：`#/data/imports?type=candidates` 和 `#/data/imports?type=positions`。

1. 资产类型为候选人时，复用候选人批次匹配范围配置。
2. 资产类型为岗位时，提供“写入后立即人岗匹配”，开启后对成功写入的岗位与系统内可用候选人匹配。
3. 导入确认页保留该配置摘要，任务详情显示匹配启动数量和跳过原因。

### 4.3 Agent 创建岗位

当前原型已经存在“AI 解析 JD—开始对话—确认后创建岗位”的入口，因此需要补充同一问题，但不新增第二套 Agent 创建页面。

1. AI 解析入口直接提供统一任务输入框，支持粘贴完整 JD、输入长段自然语言岗位需求、粘贴链接和添加 PDF、Word、表格或截图；提交后进入任务对话，不使用预置示例代替用户输入。
2. Agent 已整理出可写入的岗位资料后，在对话中使用纵向选择询问：
   - 创建岗位并立即人岗匹配。
   - 仅创建岗位。
   - 我来补充其他要求。
3. 用户可以直接用自然语言回答；结构化选择与自然语言最终转换为同一条创建命令。
4. 匹配在岗位写入成功后启动，Agent 对话显示创建结果和匹配运行入口。

## 五、Agent 候选人入库

当任务通过公开资料、用户上传简历或其他合法输入形成候选人写入建议时，在最终写入前询问：

1. 入库并匹配全部招聘中岗位。
2. 入库并匹配指定岗位。
3. 仅入库。
4. 我来补充其他要求。

指定岗位继续使用可搜索多选。用户确认后先完成身份判断、查重和写入，再对成功写入的候选人启动匹配；未解决的身份冲突保持阻塞。

## 六、状态与异常

1. 未选择文件或必填资料不足：不允许提交，使用公共字段错误态。
2. 开启指定岗位但没有选择岗位：立即显示字段错误，不使用浏览器原生提示。
3. 没有招聘中岗位：禁用“全部招聘中岗位”，说明可以先完成入库，后续从候选人详情匹配。
4. 系统没有可用候选人：岗位仍可创建或导入，匹配步骤跳过并说明原因。
5. 部分批次写入失败：只对成功写入项匹配，摘要列出跳过数量和原因。
6. 匹配运行失败：资产保持已写入状态，匹配结果显示失败和重试入口。
7. 用户中途关闭页面：导入、写入和匹配继续在后台运行，可从数据导入或资产 AI 处理记录查看。

## 七、原型验收范围

1. 候选人同公司与同部门关系：`#/candidates/candidate-linhao?tab=relations`。
2. 候选人上传并选择全部岗位：`#/candidates/new?mode=upload&match=all`。
3. 候选人上传并选择指定岗位：`#/candidates/new?mode=upload&match=selected`。
4. 候选人上传后身份审核与匹配摘要：`#/reviews/identity/candidate-linhao?from=upload&match=selected&positions=1`。该页面不是常驻导航入口；只有上传或 Agent 入库发现已有候选人或身份冲突时才进入。正常入口路径为“新建候选人—上传简历—上传并解析—发现重复身份”。
5. 手动新建岗位并立即匹配：`#/positions/new?match=all`。
6. 候选人批量导入并立即匹配：`#/data/imports?type=candidates&match=all`。
7. 岗位批量导入并立即匹配：`#/data/imports?type=positions&match=all`。
8. Agent 候选人写入选择：`#/tasks/position-vla?state=candidate-ingestion`。
9. Agent 岗位创建选择：`#/tasks/task-create-position?state=position-ingestion`。

## 八、Review 门禁

1. 同公司、同部门关系不复制成候选人手工字段，也不要求用户单独维护。
2. 匹配不会在身份查重、字段审核或正式写入之前启动。
3. 手动上传、数据导入和 Agent 写入使用同一产品口径，但保留各自已有页面结构。
4. 未开启立即匹配时，现有创建、上传、导入和 Agent 流程保持不变。
5. 匹配失败不会导致已经成功的候选人或岗位写入回滚。

## 九、实现与验证记录

1. 候选人详情已在“关联信息”中增加“人物与成果关系”切换区，同公司与同部门候选人、学术成果和合作人使用三个二级 Tab 切换显示；任职关系包含 42 条 Mock，覆盖搜索、关系筛选、公司筛选、分页和候选人详情入口。
2. 候选人简历上传、候选人批量导入、岗位手动新建和岗位批量导入复用同一组“写入后立即人岗匹配”组件与规则。
3. 候选人身份合并页会说明匹配只使用最终写入版本；完成合并后进入候选人匹配运行态。
4. 候选人入库和 Agent 创建岗位均在对话中使用纵向选择询问，保留自然语言补充入口，不新增独立配置表单。岗位 AI 解析入口已改为可直接输入长文本或添加文件的统一任务输入框。
5. 新增 `tests/stage4/candidate-relations-post-write-matching.spec.js`，7 项专项 E2E 全部通过，覆盖桌面、手机、筛选、多选、入库摘要、Agent 选择和匹配运行态。
6. 全量 E2E 为 `214 passed / 4 failed`。知识图谱失败单独复跑通过；其余 3 项在只含当前 `HEAD` 的临时 worktree 中同样失败，确认是本轮修改前已经存在的测试与 Mock 漂移，不属于本次回归。
7. 桌面截图使用 `1440 × 1000`，手机截图使用 `390 × 844`；新增页面未发现页面级横向溢出或控制台错误。
