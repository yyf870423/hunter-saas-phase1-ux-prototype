# Hunter SaaS 原型数据可获得性与一致性审查

> 2026-08-30 补充：用户侧对象已经统一为“任务”，运营侧按任务运行、任务步骤运行、资产 AI 运行和系统运行分类。本文旧分类仅用于追溯当时发现的数据问题，当前口径以 `docs/unified-task-model.md` 为准。

> 审查日期：2026-08-25  
> 当前原型：`hunter-saas-phase1-ux-prototype`，提交 `5f368e1`  
> 历史原型：`hunter-saas-phase1-prototype`，提交 `050faa2`  
> 审查范围：原型数据、页面展示、跨页面关系、用户上传与公开来源边界、运营指标及已有 Review 结论。历史原型只检查并记录问题，不修改代码。

## 一、结论

当前原型的页面结构和交互覆盖已经比较完整。本次审查最初发现 Mock 数据存在以下四类语义问题：

1. **同一对象在不同阶段原型中存在互相冲突的事实和状态。**
2. **本应由关系或记录推导的数据，被重复保存为对象本体字段或手工统计数字。**
3. **部分页面把现实中只能条件获取的信息，展示成了稳定、完整且已经确认的事实。**
4. **Hunter、用户主动上传和系统外人工沟通的边界，在旧文档与页面之间曾有冲突，现按合规边界统一。**

历史原型的问题更严重。除视觉组件和已经验证的通用交互外，历史原型中的业务数据、关系结构、人才平台流程和资产定义都不能继续作为实现依据。

截至 2026-08-25，本次发现的 7 项 P0 和 11 项 P1 已全部修正，并增加跨模块数据契约测试。Mock 数据可以继续作为产品详细设计的示例基线，但仍不能直接替代研发阶段的数据库和 API 技术设计。

## 二、审查方法

本次按四个层面检查：

1. **事实来源：** 信息来自用户输入、Hunter 正式资产、用户上传文件、公开数据源还是运营埋点。
2. **字段归属：** 信息属于资产本体、资产之间的关系、任务快照还是统计结果。
3. **时间口径：** 不同页面显示的是同一时点，还是有明确版本和时间的历史快照。
4. **可获得性：** 信息是否稳定可得；条件不可得时，页面是否有“未获取、待核验、来源失效”等状态。

通过静态代码检查和结构化计数脚本核对了公司、联系人、岗位、候选人、人才版图、论文、专利、业务主线、支线任务、设置和运营端数据。自动化页面测试通过只能证明页面可访问和交互可执行，不能证明业务数据语义一致。

## 五、现实数据可获得性

### 5.1 可稳定获得或由 Hunter 自己生成

| 场景           | 可稳定获得的数据                                                     | 主要来源                              |
| -------------- | -------------------------------------------------------------------- | ------------------------------------- |
| 用户与工作空间 | 账号、工作空间、订阅、用量、通知、授权和审计元数据                   | Hunter 账号、支付和事件系统           |
| 业务资产       | 用户手动录入、上传并确认的公司、岗位、候选人、联系人、机会和版图内容 | 用户输入、导入文件、已确认 Agent 结果 |
| 业务过程       | 主线、支线任务、执行计划、检查点、等待状态、写入决定和失败记录       | Hunter 任务与业务事件系统             |
| 邮件           | Hunter 发出的邮件、发送状态，以及邮箱协议能够读到的回复              | 用户授权邮箱；每次发送前确认          |
| 用户上传资料   | 用户主动上传的候选人简历、批量压缩包、文本字段和附件                 | 用户主动上传或文件导入                |

### 5.2 只能条件获得，必须有缺失和核验状态

| 场景           | 条件数据                                                     | 限制与正确展示方式                                                                                     |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 公司调研       | 融资、估值、市值、福利、薪酬、面试流程、组织结构、各地点业务 | 公开程度和时效差异很大；记录来源和观察时间，允许“未获取、推断、待核实、已确认、已过期”                 |
| 联系人         | 姓名、角色、公司关系、邮箱、手机号、引荐路径                 | 公开网络通常不能稳定获得个人手机和有效邮箱；不得伪造，找不到时保留联系缺口                             |
| 招聘机会与岗位 | 招聘信号、HC、预算、完整 JD、汇报关系和合作意愿              | 公开招聘只能证明存在招聘迹象，不能证明客户合作、预算或完整岗位；信息不足先形成机会，不直接形成正式岗位 |
| 候选人         | 公开履历、工作经历、论文专利、联系方式、意愿、薪酬、到岗时间 | 公开履历可能过期；意愿、薪酬和到岗时间主要来自候选人回复或猎头补充，不能由模型当作事实推断             |
| 人才版图       | 公司生态、组织、方向、人物和关系                             | 只能表达“已发现并有证据支持的范围”，不能声称覆盖未知市场总体；每条关系保留证据、时间和确认状态         |
| 论文           | 标题、作者、机构、摘要、标识和被引数                         | 数据源覆盖不一致；被引数随时间变化，作者机构可能多值，作者与候选人身份必须另行核验                     |
| 专利           | 申请号、公开号、申请人、发明人、摘要和法律状态               | 法律状态会变化且数据有延迟；必须保存查询来源和日期，不能用授权日推断当前有效性                         |
| 公开网络证据   | 页面正文、发布时间、链接和快照摘要                           | 页面可能失效、反爬或变更；页面不可访问时保留失败原因，不能把搜索摘要当作已经核验的正文                 |

### 5.3 云端不能直接获得

1. 猎聘、脉脉等认证人才平台中的实时页面、账号状态、候选人详情和执行过程。
2. 用户在 Hunter 之外使用外部网站或工具时的搜索、翻页、页面错误和登录恢复过程。
3. 用户电话、微信、线下沟通的真实内容，除非用户主动写入普通跟进记录或上传材料。
4. 候选人的真实求职意愿、薪酬底线、竞业和到岗承诺，除非候选人或猎头提供。

Hunter 只在用户主动上传文件后知道“已收到一个候选人批次”。系统不生成跨端任务、不识别外部设备，也不展示认证平台内部步骤。

## 六、统一数据基线建议

### 6.1 单一事实源

1. 每个正式资产只保留一份 Canonical Mock 数据，通过稳定 ID 被所有页面引用。
2. 候选人 × 岗位匹配、候选人 × 岗位推进、联系人 × 公司、候选人经历 × 公司、成果署名 × 人物等关系独立保存。
3. 公司详情、候选人详情、岗位详情、人才版图和运营统计只读取关系，不复制第二份事实。
4. 工作台、业务主线、支线任务和资产页共享同一个当前状态；历史变化通过事件和版本表达。

### 6.2 外部事实状态

外部或 Agent 生成字段至少需要以下公共语义，不要求所有字段都在 UI 中同时展示：

```text
value
source
observed_at
verified_at
confidence
availability: available | missing | failed | stale
review_state: inferred | pending | confirmed | rejected
```

### 6.3 统计与商业数据

1. 套餐、价格、额度和权益来自同一个版本化套餐目录。
2. 所有页面数量从资产与关系计算，不允许另写展示数字。
3. 运营指标必须定义分子、分母、时间范围、排除规则、刷新频率和数据来源。
4. 成本指标明确模型、搜索、邮件、存储和通知如何归集到任务与工作空间。

## 七、需要补充的自动检查

| 检查             | 失败示例                                               | 门禁                           |
| ---------------- | ------------------------------------------------------ | ------------------------------ |
| 引用完整性       | 关系引用不存在或已删除的资产 ID                        | 构建失败                       |
| 派生数量一致性   | 公司声明 4 位联系人，但实际关系只有 2 位               | 构建失败                       |
| 字段归属         | 候选人本体出现全局匹配分或岗位推进阶段                 | 构建失败                       |
| 跨页事实一致性   | 同一候选人在不同页面出现不同公司、地点或资料版本       | 构建失败；有版本时必须显式标注 |
| 学术身份一致性   | 候选人与论文关联，但不是作者且没有关系类型             | 构建失败                       |
| 标识与来源一致性 | Crossref 论文展示固定 OpenAlex/arXiv 标识              | 构建失败                       |
| 云端边界         | 云端页面出现人才平台登录、翻页、详情读取或平台消息发送 | 构建失败                       |
| 套餐一致性       | 用户端与运营端套餐价格或额度不同                       | 构建失败                       |
| Mock 身份冲突    | 两个不同自然人共享手机号或邮箱                         | 构建失败或明确进入身份冲突样例 |
| 指标定义         | 运营指标没有口径和时间范围                             | Review 不通过                  |

## 八、处理优先级

### P0：先统一数据，再继续扩展原型

1. 移除候选人本体上的全局匹配分和推进阶段。
2. 建立公司、岗位、候选人、关系和主线的统一 Mock 数据源。
3. 修复论文详情固定标识、摘要和来源的问题。
4. 统一用户上传、公开来源、邮件和系统外沟通边界。
5. 统一套餐与权益目录。

### P1：原型冻结前完成

1. 统一人才版图批次与总量口径。
2. 为外部事实增加来源、时间、可获得性和确认状态。
3. 修正论文作者机构结构和专利法律状态。
4. 完成运营指标字典和邮件调度状态模型。
5. 更正已有 Review 结论并补充语义测试。

### 历史原型处置

历史原型保留为视觉、组件和交互探索档案。以下内容明确禁止复用：

1. 六资产模型、联系人从属关系和非资产化招聘机会。
2. 候选人全局匹配分、全局招聘阶段和岗位目标人数。
3. 云端猎聘、脉脉自动化及平台消息动作。
4. 人才摸排覆盖百分比、数组位置生成关系和手工汇总数量。
5. 历史 Mock 的论文作者关联与固定标识。

## 九、Review 结论

本次 Review 发现的问题不是视觉细节，而是会直接影响详细设计、API、数据库、Agent 上下文和运营口径的业务语义问题。当前原型可以继续用于 UX 验收，但在上述 P0 问题修正并通过语义自动检查前，不能声明“跨页面名称、数量和关系保持一致”，也不能将现有 Mock 文件视为研发数据模型。
