# 原型阶段三组件边界

> 状态：组件边界已按阶段三实现并完成回归，等待阶段三人类审批。
>
> 本文件约束阶段三如何复用阶段二组件并新增业务组件，防止四条主线变成四份重复页面或单一页面换文案。

## 一、公共外壳

以下结构只能有一套实现：

1. 业务主线历史、收起与展开、新建工作入口。
2. 主线头部、状态、暂停、继续、终止和删除菜单。
3. 对话滚动区、用户消息、Hunter Markdown 回复和流式状态。
4. 执行计划、计划调整、相关内部任务和任务详情检查。
5. 对话输入、附件、授权模式、发送、停止生成和输入框自动高度。
6. 加载、流式中断、权限受限、局部失败和等待外部状态。

公共外壳通过稳定接口接收主线身份、计划、任务、对话事件和业务审核入口；不能在外壳中硬编码某一种主线的字段。

## 二、主线剧本配置

四条主线分别维护独立剧本配置，至少包括：

1. 主线身份、来源对象、目标和默认授权。
2. 渐进阶段、每阶段可见对话和推进条件。
3. 计划步骤、内部任务、调整规则和结束条件。
4. 专用结果类型、审核入口、等待对象和恢复动作。
5. 通用状态和专用分支状态。

剧本配置不能只提供标题和文案；必须提供不同的过程对象、业务命令、结果结构和分支处理。

## 三、受控结果组件

| 组件         | 使用主线 | 必须显示                                                                       | 不负责                           |
| ------------ | -------- | ------------------------------------------------------------------------------ | -------------------------------- |
| 联系人审核   | 客户开发 | 姓名、角色、公司关系、手机、邮箱、来源、可信度、是否可联系                     | 自动发送消息、完整联系人资产管理 |
| 候选人审核   | 岗位招聘 | 完整候选人资料、得分、理由、风险、证据、建议动作                               | 联系候选人、改变推进阶段         |
| 人才版图批次 | 人才摸排 | 公司、组织、方向、人物、关系、来源、冲突、待补充信息与下一步、用户确认写入决定 | 猜测未知关系、显示虚假百分比     |

人才版图批次新增数据驱动的 `RelationshipCanvas`。组件只负责在组织与方向、公司生态、方向与角色、人物关系、人才流动、联系路径和学术脉络之间切换，展示节点、关系方向、证据、观察时间和确认状态；它不拥有业务关系事实，也不把坐标写回业务数据。正式实现可替换底层布局或渲染引擎，但必须保持同一关系数据、明细审核和 Agent 探索口径。
| 岗位匹配审核 | 候选人求职 | 系统内岗位、分数、理由、风险、缺口、沟通要点 | 搜索公开市场岗位、自动联系候选人 |
| 外部等待 | 客户开发、岗位招聘、候选人求职 | 对象、渠道、开始时间、最近检查、下一次处理安排 | 持续运行动画、持续消耗用量 |

招聘机会摘要、证据摘要和少量比较结果属于只读内容，由动态 Markdown 根据实际字段渲染，不再作为场景专用受控组件。只有需要批量选择、业务审核、正式写入或产生外部影响的结果才进入上表组件。

## 四、数据与组件映射

1. Agent 普通输出统一映射为 Markdown，不允许直接注入 HTML。
   - 标题、段落、有序与无序列表、引用、表格、链接、强调、行内代码、代码块和分隔线使用统一 Markdown 样式。
   - 授权、确认和审核选项不属于 Markdown，由 Hunter 受控组件独立渲染，不能回退为浏览器默认控件。
   - 证据摘要、少量结果、比较结果、阶段总结和招聘机会摘要不再建立场景专用结果卡片，优先使用 Markdown；只有需要稳定业务操作的数据才进入受控组件。
2. 受控组件只接收代码校验后的结构化数据；未知只读结构降级为 Markdown 文档。
3. 涉及正式写入、外部操作或业务审核的未知结构必须停止，不能降级放行。用户确认只能决定业务上不确定的内容是否写入，不能绕过结构、类型和安全门禁。
4. 自然语言决定与受控审核操作映射到同一业务命令和对象集合。
5. 待确认内容默认不由自动流程写入；用户明确确认写入时，必须保留确认人、确认时间、原始冲突或不确定说明。
6. Mock 数据中的人数、状态、对象名称和关联去向必须在主线历史、执行计划、对话、审核和结果摘要中一致。

## 五、响应式映射

1. 桌面中量详情使用左侧选择、右侧详情的主从结构：右侧详情宽度必须大于左侧列表，左侧当前行必须具有选中强调和指向右侧的 SVG，右侧必须显示对应的详情类型标题；移动端使用全屏覆盖层。
2. 桌面大型审核占用主要工作区；移动端使用完整页面式审核。
3. 桌面表格在移动端转换为字段分组列表，不使用横向滚动。
4. 主线历史在桌面可收起，在 iPad 和 iPhone 作为可关闭导航面板。
5. 组件 normal、loading、empty、error、disabled、permission-limited 和 waiting 状态使用同一 token 与反馈规则。
