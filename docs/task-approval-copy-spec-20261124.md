# 任务确认与授权的文案组织规范

状态：2026-11-24，产品负责人确认“同意，推送原型并更新详细设计”。本次仅更新并推送原型、原位同步飞书详细设计，不改 1420、后端或正式官网。更新飞书前重新同步在线最新正文与块结构，禁止用旧本地副本覆盖。

## 1. 结论

用户应看到“将对什么内容做什么、产生哪些实际变化”，而不是被要求笼统地“授权 Agent”。“执行前确认”是任务模式；每次操作的按钮应使用具体业务动作。

推荐的信息顺序：业务问题标题 → 对象与范围 → 本次实际变化及结果去向 → 影响决定的依据/缺口/边界 → 具体动作与拒绝按钮。

这是一份内容合同，不是要求所有场景机械展示相同字段。没有变更对比的新增操作不显示空的“旧值”；没有附件不必创建空附件表格；必要事实缺失时应补充或保留待核实，不编造。

## 3. 先区分三种用户决定

### 3.1 业务分支选择

例如“是否继续核实联系人”。用户是在决定下一步做什么，不是在授予额外系统权限。使用“继续核实联系人 / 暂不继续”，说明“只核实资料，不建档、不发送邮件”。

用户已经明确要求、且属于已获准任务范围的普通读取、检索、分析与比较，不再机械追加一次相同确认。旧设计要求先完成机会入库决定、再询问是否继续核实联系人的顺序仍保留；只是把后一节点正确表达为业务分支选择，而非第二次权限授权。

若将扩大对象/数据源范围、引入未授权付费行为或访问受限内容，应先明确新增影响，并遵循相应授权要求，不能以“只读”绕过。

### 3.2 业务变更确认

例如保存机会、修改岗位、加入储备、更新人才地图、保存跟进记录。先说明真实的待执行变更，再提供与动作对应的按钮。

点名、查看、排序、打开详情或输入一个业务目标，不等于确认后来生成的写入草稿。对既有规则要求独立确认的操作，仍需确认当前版本。

### 3.3 系统访问授权

例如连接邮箱、授权读取某类资源。此时可以使用“授权读取邮箱”等真正的权限文案，展示访问范围与有效性。

不把任务内一次业务变更称作永久系统授权；不把授权模式切换、保存资料和发送邮件揉成同一次点击。

## 4. 正文组织规则

### 4.1 标题回答“是否做这件事”

- 优先直接表达动作和对象，例如“将顾言川加入这个岗位的储备？”、“保存这条潜在招聘机会？”。
- 不使用“需要你授权本次执行”“是否继续处理”作为有明确业务动作时的默认标题。
- 不显示 Skill、工具、工作流代号、执行节点名。结果/草稿版本可放在次要位置，不能代替业务内容。

### 4.2 对象范围必须可核对

- 写明目标对象及必要的区分信息：候选人姓名与公司、目标岗位与公司、图谱名称与图页、机会名称等。
- 同名、目标不唯一或范围不确定时先澄清，不给一个能“确认全部”的按钮。
- 批量处理说明总范围及新建、更新、不变、跳过、待核实数量，口径不能混用文件数、人物数与记录数。
- 短名单直接列出；长名单提供摘要及可展开的完整范围。批准整批时明确批准的是完整批次，而不是屏幕当前页或前几条。
- 用户明确排除的对象、条件和例外必须保留。编号引用绑定当时的结果顺序，排序变化不得改掉所指对象。

### 4.3 展示实际变化，不重复原要求

- 新增：说明新建什么、几条、保存到哪里。
- 修改：展示目标对象和有变化字段的旧值 → 新值；大段 JD、资料或邮件可展开完整查看，不用摘要替代真正被提交的内容。
- 不变、已存在和跳过不计成新增或更新。写入依据与未核实部分分开，不因用户点击而把推测变成已核实事实。
- 关联变更必须一起说明。例如加入岗位储备同时同步人才梳理，不能在主操作成功后隐式附带另一项未披露变更。

### 4.4 依据和风险只写影响决定的内容

- 依据可来自当前用户指令、已确认岗位要求、当前结果、已核验来源等；不能把模型建议当作用户已确认要求。
- 附带“不会自动联系”“缺少详细 JD，不创建岗位”等确有误解风险的边界；不在每张卡机械堆叠所有全局限制。
- 会对外发送、删除或产生持续效果的动作，在点击前说明结果和恢复限制，不能只放进 Tooltip。
- 当前没有的数据如匹配分、费用、人数、来源或时间保持未知，不让模型凑齐模板。

### 4.5 按钮表达可预见的业务结果

- 主按钮由动作确定：确认入库、保存修改、确认加入储备、保存人才地图、保存跟进安排、创建周期任务、确认发送。
- 次按钮由拒绝后的结果确定：暂不保存、保留原内容、暂不加入、暂不发送、暂不创建等。
- 取消一个安排时，正向按钮是“取消这次安排”，反向按钮是“保留原安排”；不能都用抽象的“执行 / 暂不执行”使方向难辨。
- 改要求仍使用原对话，不恢复强制勾选和提交，不添加一套与原对话争用的业务表单。
- 一般操作不再要求手动输入“确认”。删除工作空间等既有高风险专用门禁不在本次取消范围内。

### 4.6 点击后的状态不冒充完成

- 正在提交：明确“正在提交确认”，锁住同一请求防重复；只有确已开始写入时才说“正在保存”。
- 已受理但未完成：“已确认，正在处理”；不显示“已保存成功”。
- 已完成：显示实际新增、更新、未变与失败项，链接到真实结果；数据写入、步骤完成和整个任务完成不混为一谈。
- 明确失败：说明可核实的失败范围、原因及恢复方式，保留草稿。只有确认完全未写入，才能说“本次未写入任何内容”。
- 结果未知：先查询状态，提示“暂时无法确认是否完成，正在核对”；不鼓励用户反复点击或直接重发邮件。
- 部分成功：已成功项保留，只恢复可安全重试的失败项。
- 对象、输入、附件、版本或权限变化后，旧确认失效；先展示更新后的范围，再确认。不会因为改了文案就沿用旧请求 ID。

## 5. 可直接用于设计的例子

以下人名沿用本地虚构原型，邮箱使用示例域名；不是实际发送或业务结果。

### 例一：加入岗位储备，分清新增和保持原样

用户要求：“将 85 分以上的人加入岗位储备，但不要选择赵星羽。”

标题：**将顾言川加入岗位储备？**

- 目标岗位：星澜机器人 · 具身智能 VLA 算法负责人。
- 新增 1 位：顾言川。
- 保持 3 位原阶段：林昊、周明远、陈楚宁已在该岗位流程中，不退回储备。
- 赵星羽不在本次范围；未列出的人选不变。
- 新增储备关系同步到该岗位人才梳理，不发送联系消息。

主按钮：**确认加入储备**；次按钮：**暂不加入**。

成功后的文案：“顾言川已加入岗位储备，人才梳理已同步；其余 3 位保持原阶段。未发送联系消息。”不能写“新增 4 位候选人”。

### 例二：潜在机会入库，不替用户确认真实需求

标题：**保存这条潜在招聘机会？**

- 所属公司：星澜机器人。
- 机会：机器人团队扩张潜在招聘机会。
- 依据：官网岗位变化及融资公开信息，详细来源可查看。
- 保存到招聘机会列表。实际 HC、预算、合作意愿和完整 JD 仍待核实。
- 本次不创建正式岗位，不保存联系人，不发送邮件。

主按钮：**确认入库**；次按钮：**暂不保存**。

完成机会入库或暂缓决定后，若需要选择下一步，使用“是否继续核实招聘联系人？”及 **继续核实联系人 / 暂不继续**；不要再写“授权执行调研”。

### 例三：简历导入与约定匹配范围

用户已要求“导入后匹配当前岗位”。

标题：**导入这批候选人资料，并匹配当前岗位？**

- 新建 9 位候选人，补充 2 位已有候选人的资料；逐项差异与来源可查看。
- 另有 1 位身份存在冲突，本次不写入、不参与匹配。
- 成功写入的 11 位候选人匹配“具身智能 VLA 算法负责人”；不扩到其他岗位。
- 匹配失败保留已成功写入的资料，不发送联系消息。

主按钮：**导入并匹配**；次按钮：**先不导入**。

若用户只要求导入，则按钮改为“确认导入”，正文不能自动加上匹配。选谁和如何处理冲突仍由原对话/已有身份核实决定，不借此恢复强制勾选。

### 例四：保存组织梳理结果

标题：**保存本轮公司组织梳理结果？**

- 范围：当前已列明公司的组织、关键岗位、任职人与已核实关系，完整对象和变更可展开。
- 保存到已明确的目标人才地图，按公司分图页；新建或更新必须根据当前真实目标说明，不预填虚构名称和数量。
- 未知任职人和关系冲突继续标记待核实，不把未知岗位变成确认空缺。
- 不创建候选人，不加入岗位储备，不对外联系。

主按钮：**保存人才地图**；次按钮：**暂不保存**。

若尚未决定保存到哪一张地图且无法唯一确定，应先询问目标，不能用这个按钮替用户选择。

### 例五：跟进安排及取消

标题：**保存下次跟进安排？**

- 来源：当前任务中的星澜机器人招聘机会。
- 事项：核实完整 JD。
- 时间：用户已明确的未来日期及 10:00（北京时间；实际界面替换为有效日期，不沿用示例占位时间）。
- 在所属任务内建立跟进安排；到时提醒，不自动联系客户。

主按钮：**保存跟进安排**；次按钮：**暂不保存**。

若是取消原安排，标题改为“取消这次跟进安排？”，列出原事项与时间，说明历史记录保留；按钮为 **取消这次安排 / 保留原安排**。

### 例六：邮件发送，核对的是完整邮件

标题：**向陈雨发送这封邮件？**

- 发件人：当前已连接的工作邮箱（界面展示实际地址）。
- 收件人：陈雨 `chenyu@example.com`；抄送、密送按实际内容完整展示。
- 主题：关于机器人研发岗位合作的沟通。
- 正文、附件：发送确认区展示实际完整正文及附件清单；无附件明确“无附件”，不能只给模型生成摘要。
- 本次仅发送这一封。发送后不能保证撤回，不自动发送后续跟进邮件。

主按钮：**确认发送**；次按钮：**暂不发送**。

收件人、主题、正文或附件改变后重新核对，上一版确认不沿用；发送状态未知时先查询，不能盲目再次发送。

### 例七：创建周期计划，不套用“只影响这一步”

标题：**创建每周招聘变化检查任务？**

- 跟进范围：用户明确的公司与主题，显示完整范围。
- 周期：每周一 09:00（北京时间）。
- 后续将按该计划持续运行，遵守已经约定的处理范围；若后端尚不能确定下一次时间，留待调度确认，不生成时间假象。
- 发现按已有洞察和待审核规则处理；单资产确认、身份核实、邮件发送等原有门禁继续生效。
- 可从周期任务中暂停或调整计划。

主按钮：**创建周期任务**；次按钮：**暂不创建**。

这里确认的是一个持续配置，不能只写“本次授权、不影响以后”却隐藏后续周期运行。修改计划时展示旧周期/范围 → 新周期/范围，按钮为“保存计划修改 / 保留原计划”。

## 6. 文案生成与程序边界

1. 操作类型、对象 ID/集合、当前草稿与结果版本、变更对比、数量、去向、可执行性、状态及回执由结构化事实和代码校验确定，不能让模型随意生成。
2. 标题和按钮从合法操作类型映射到文案模板；模型可以在已核实事实范围内组织依据和风险，但不能扩展对象、增加动作、修改人数或补造来源。
3. 用户能看懂且可核对的摘要，必须与真正提交的结构化请求一致。摘要确认之后不能由另一轮模型自行改写待执行操作。
4. 由服务端将明确的用户决定绑定本次请求 ID、版本及幂等键。自然语言确认和按钮点击必须走同一受控执行边界，不能一个有门禁、另一个仅发送通用“确认”。
5. 普通业务文字、用户确认事件、事实依据分别保存。用户点了同意，不代表资料已核实，也不代表业务操作已经成功。

## 8. 交叉 Review

- 已核对执行前确认与仅分析、自动执行、单资产首次确认、身份冲突、周期计划和邮件发送的边界。
- 明确修正上一版本地原型中的两项泛化：所有操作使用同一“授权本次执行”文案；把继续只读核实称为新增授权。周期计划也需避免套用一次性操作的边界话术。
- 本稿已获确认；原型和飞书在上述授权范围内同步。实际服务端请求、版本、幂等、回执和恢复仍需研发接入，不能把有限本地演示视为生产能力。
